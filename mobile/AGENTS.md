# Android shell

This directory contains the committed Capacitor Android shell for the production
SPA. Remote access behavior and operator setup live in
[remote-access.md](../docs/specs/remote-access.md) and
[remote-access-setup.md](../docs/architecture/remote-access-setup.md). Emulator
ownership and evidence rules live in [e2e/AGENTS.md](../e2e/AGENTS.md).

The Android project is committed because native configuration and plugins are
product code. Generated build outputs, `local.properties`, the copied SPA, and
private service configuration remain ignored.

## Build and release

Use `make apk` for the debug APK and `make apk-release` for a signed release.
The scripts require JDK 21 and an Android SDK, verify the SPA bundle metadata,
run JVM tests, and then assemble. Keep the root, frontend, and mobile
`packageManager` pins identical.

Release signing inputs are external secrets. Do not commit keystores,
credentials, `google-services.json`, or generated signed artifacts. Follow the
exact release and recovery procedure in
[remote-access-setup.md](../docs/architecture/remote-access-setup.md#test-production-builds-before-a-release).

Generate launcher artwork through `mobile/scripts/generate-icons.mjs` and keep
adaptive foreground, background, legacy, and notification assets consistent.

Only the debug manifest permits cleartext traffic, for the local emulator
harness. The release manifest must remain TLS-only. Detailed endpoint,
certificate, LAN, and native network-adapter contracts are owned by the remote
access spec and networking code; keep this guide at the shell boundary.

## Fixed origin and native seams

The shell loads the SPA from its fixed Capacitor origin. Do not replace it with
a remote page. Cross-origin HTTP and WebSocket access goes through the guarded
native adapters, preserving private-certificate verification and bounded
streaming behavior.

All browser fallbacks are inert, and every Capacitor dynamic import is guarded
by `isNativeShell()` so browser builds never resolve native modules. The main
seams under `frontend/src/lib/native/` are:

- network trust, HTTP, and WebSocket adapters;
- lifecycle and hardware-back handling;
- app lock and startup pairing adoption;
- QR scanning and shell-local keybindings;
- bundle synchronization; and
- push registration, presentation, retraction, and tap routing.

Startup must process a `#pair=` invitation before first-run routing. Pairing by
QR and by link uses the same payload validation and endpoint adoption. Neither
path stores SSH credentials.

The app-lock cover is mounted above the still-running app and marks underlying
content inert. Raise the cover on pause so task-switcher snapshots cannot expose
the app. Resume decides whether authentication is due. Preserve the distinction
between an app pause and the pause caused by the biometric prompt itself.
Hardware back uses the lifecycle/keybinding dismissal path before leaving the
app; read `frontend/src/lib/native/lifecycle.ts` before changing its ordering.

## Bundle updates

`BundlePlugin`, `BundleStore`, and `native/bundleSync.ts` form one update
protocol. Preserve these contracts:

- The APK-bundled SPA is the fallback and identifies itself through
  `bundle-id.txt` generated by the same fixture rule as `internal/bundle`.
- Verify version, shell compatibility, bundle identity, digest, and signature
  before staging. Never activate partially downloaded or unverified bytes.
- Store state atomically. On boot, select the staged bundle before
  `super.onCreate`; the WebView must never observe an intermediate root.
- A staged bundle becomes accepted only after the launched page reports healthy.
  The native watchdog rolls back a launch that never reports health.
- Keep previous bytes until the new launch is accepted. Rollback and retry state
  must distinguish a failed candidate from the known-good bundle.
- Download, verification, retry, and rollback remain silent. User-facing state
  is limited to an available staged update or an incompatible shell.

`BundleStore` unit tests run on the JVM. Android's `org.json` stubs throw, so the
test classpath must retain a real JSON implementation without packaging it into
the app.

## Push notifications

The shell uses its own data-message plugin because presentation and retraction
must share one identity across push delivery and the live socket.

- `TrayNotifier` owns notification identity and decisions without Android
  dependencies; both push and in-app paths use it.
- `AndroidTray` owns only Android channel, builder, cancel, and launch-intent
  operations.
- `PushMessagingService` receives data messages and token changes.
- `PushPlugin` owns permission, token exposure, foreground state, presentation,
  retraction, and tap delivery to the web layer.
- Drop presentation while the app is foregrounded, where the socket path already
  presents it. Never drop retraction.
- The stable tray tag is `<backendId>|<notificationId>` in every implementation.
  Keep PendingIntent identity derived from that tag.
- Carry the notification target as opaque JSON through Java. Parse it only in
  the frontend. Handle both warm `onNewIntent` and cold-start intents, retaining
  a cold tap until the page consumes it.
- Request notification permission only after the app lock first passes. Unpair
  and backend removal unregister over the connection before detaching it.

`mobile/android/app/google-services.json` is optional and gitignored. The APK and
JVM tests must build without it. Real Firebase delivery is an explicit manual
emulator case selected by `AO_ANDROID_PUSH_CREDENTIAL`; automatic tests prove
only composition, registration, redaction, and tray behavior.

## Local data and identity

Cloud backup and device-to-device transfer remain disabled. Preserve
`allowBackup="false"`, `fullBackupContent="false"`, and exclusions for every
storage domain in both backup rule sections. A restored device signing key would
duplicate one registered device identity across two phones.

Current biometric locking gates the screen, not storage encryption. The device
key and cached thread replica remain protected by Android's app sandbox and disk
encryption rather than a user-authenticated Keystore key. Do not describe the
lock as encrypting stored data.

## Verification boundaries

`make e2e` proves cross-origin browser transport against the real Go server.
`make e2e-android` proves WebView boot and native plugin integration only when an
emulator is actually attached; a no-device skip is not evidence. Signed APK
lifecycle and real push delivery are separate explicit manual modes.

Native network changes require JVM tests for certificate failures, late upload
errors, bounded reads, and socket framing, plus the emulator path when WebView or
Android behavior matters. Preserve the original failure cause until JavaScript
consumes it; cleanup or upload cancellation must not replace a certificate or
transport error with a generic missing-transfer error.

## Deferred

iOS, Android share-target support, hardware-backed device keys, and encrypted
replica storage remain out of scope until their designs and release workflows
are explicitly approved.
