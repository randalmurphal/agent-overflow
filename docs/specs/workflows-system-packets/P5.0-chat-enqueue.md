# Packet P5.0 — user-directed enqueue-from-chat producer

First M4 packet: the missing producer for §7.2 (Enqueue from chat,
D4.5 as amended by "M4 rulings (user decisions, 2026-07-13)" in
`docs/specs/workflows-system-decisions.md` — read that section in full
first; it governs this packet). Spec precedence:
`docs/specs/workflows-system-decisions.md` →
`docs/specs/workflows-system-ui/UI-SPEC.md` §7.2 →
`docs/specs/workflows-system.md`.

Product shape (the ruling, verbatim intent): a **first-party,
self-describing tool** available to interactive threads (normal chat +
the workflow triage thread), invoked **when the user asks** — its
description must tell the agent what it is and that it must not enqueue
unprompted. A settings toggle gates the feature: off = the tool is
absent from sessions, not hidden. The §7.2 confirm card is the commit
point — chat NEVER enqueues silently.

## Work plan

1. **Provider capability verification (do this FIRST).** Confirm, per
   spike policy, that (a) Claude Code CLI accepts a streamable-HTTP MCP
   server via `--mcp-config` (type/transport field and header support
   for auth), and (b) Codex app-server sessions can use an HTTP MCP
   server configured via `[mcp_servers.<name>]` (+ `http_headers`) and
   that per-thread disable via the existing `DisabledMcpServers`
   scoping applies. Record exact findings (flag names, config shapes,
   versions) in the report's ASSUMPTIONS. If either provider cannot
   attach an HTTP MCP server, STOP — BLOCKED with your analysis and the
   closest workable alternative (e.g. stdio shim binary); do not build
   the alternative unilaterally.
2. **First-party MCP endpoint.** In-process MCP server (streamable
   HTTP) on the existing local server, exposing exactly one tool:
   `enqueue_workflow_run`. Implement the minimal MCP protocol surface
   by hand (initialize / tools-list / tools-call over JSON-RPC) — no
   new dependency. Auth: require the transport token (header), never
   trust loopback alone. Inputs: `project` (id or slug), `workflow`
   (definition id), `goal` (string), `seeds` (object, optional),
   `base_branch` (optional). Tool description must state: what it does,
   that a confirmation card is shown to the user (nothing enqueues
   without approval), and that the agent must invoke it **only when the
   user explicitly asks** to queue work — never proactively.
3. **Settings toggle.** New setting (e.g. `workflowChatEnqueue`, bool,
   default **true**) in `internal/settings` with validation + wire +
   settings UI checkbox beside the existing workflow settings. ON →
   the MCP server is attached to interactive threads (normal chat +
   triage; NOT workflow phase threads, NOT design/studio unless trivially
   the same path); OFF → absent from newly started sessions (document
   in the report how mid-flight sessions behave; do not build session
   restart machinery).
4. **Tool call → persisted proposal.** A `tools/call` validates:
   project exists, definition resolves and is valid, seeds typecheck
   against the definition's input schemas (reuse `internal/workflow/def`
   validation), base branch defaults like intake. Persist a proposal as
   a thread timeline item on the calling thread (survives reload;
   states: pending / queued / dismissed). The tool RESULT tells the
   agent the proposal was recorded and awaits user confirmation (the
   turn ends cleanly; no polling). Invalid input → tool error result
   with the precise validation message (errors are user-facing state).
5. **Card in the thread timeline.** Pending proposals render
   `WorkflowConfirmCard` in the thread transcript at their timeline
   position. Queue it → existing enqueue path with `source: "agent"`
   (and the §7.2 identical-queue-citizen semantics), card flips to its
   queued/receipt state. Edit → §7.1 intake prefilled from the proposal
   (`WorkflowIntakePrefill`); queueing from intake resolves the
   proposal. Dismiss → resolved-dismissed. Resolved state persists and
   renders (no dangling pending cards after action). View-only remote
   sessions: actions disabled with the standard `Local only` title.
6. **Transport classification.** Any new App-bound method (proposal
   list/resolve, etc.) classifies per `internal/transport/AGENTS.md`
   (`LocalOnlyMethods` for anything touching enqueue/provider/local
   state) + methodgen regen committed.
7. **Tests.** Every seam: MCP endpoint (auth required, tool schema,
   validation errors, happy path), settings gating (config
   present/absent per provider), proposal persistence + reload, card
   actions (queue/edit/dismiss incl. view-only), def-validation reuse.
   e2e: existing specs must keep passing; add a flow spec ONLY if the
   harness's mock providers can already drive an MCP tool call without
   touching `e2e/src/harness.ts` — otherwise state in the report that
   e2e coverage needs a harness follow-up (do not touch the harness).
