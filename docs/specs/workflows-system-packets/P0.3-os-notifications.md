## Intent

Wire OS notifications end to end as a reusable pipe: register the Wails v3
notifications service, request authorization at startup where the platform
requires it, provide one internal Go send helper carrying a typed deep-link
payload, and handle notification **activation** (click) by emitting an event
the frontend consumes. The workflows system (M3) will send through this pipe;
this packet delivers the pipe only — no workflow-specific anything.

## Design decisions (binding)

- **Registration:** desktop entry path. Registration and authorization MUST
  degrade gracefully: on platforms/environments without notification support
  (headless Linux, WSL without a daemon) the app starts normally, logs the
  condition once, and the send helper returns a visible error — never a
  crash, never a silent no-op, never a blocked startup. The harness
  (`--harness`, headless) must keep working.
- **Send helper:** one internal method on `*App` (unexported; NOT a bound
  method), signature along the lines of
  `notifyOS(title, body string, target NotificationTarget) error`, following
  root-package naming conventions. `NotificationTarget` is a small typed
  struct: `Kind string` (json `kind`; values `thread` or `none` for now) plus
  `ThreadID string` (json `threadId`, omitempty). The target rides in the
  notification's user data.
- **Activation:** the service's activation callback decodes the target and
  emits ONE new event to the frontend via the transport-aware emit helper,
  following the documented add-a-channel path (no generic passthrough).
  Event name: `notification:activated`, payload = the target object.
- **Frontend handling:** subscribe where other server-push events are wired.
  `kind === "thread"` with a known thread → focus/open that thread's pane
  using the existing store affordance; unknown thread or `kind === "none"` →
  a console-visible log line, no crash. No new UI chrome.
- **Harness trigger:** add `HarnessNotify` on the Harness receiver (inherits
  the registration gate + LocalOnly marking; regen methodgen + TS bindings
  per conventions). It calls the same send helper (error surfaced in the
  RPC response, not swallowed) and ALSO synthesizes an activation of the same
  target so e2e can assert the full frontend path without OS interaction —
  make it explicit in code that the synthetic activation bypasses only the
  OS layer, nothing else.
- **e2e:** one spec following `e2e/tests/harness.spec.ts` conventions (no
  sleeps; event/RPC-driven): `HarnessNotify` with a seeded thread target →
  the frontend receives `notification:activated` and the thread focus
  behavior happens; and a `none` target → the logged no-op path.
- **Verification honesty:** OS-level presentation + click-through on the real
  Windows/WSL launcher CANNOT be verified in your environment. State this in
  the report as an explicitly unverified surface requiring user-assisted
  verification. Do not claim it works.
