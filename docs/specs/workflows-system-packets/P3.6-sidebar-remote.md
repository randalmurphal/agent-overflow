  (parked, "to dispose"); done + non-empty disposition = resolved.
  `WorkflowListItems("")` returns ALL projects' items unpaged — the

  (`internal/transport/event_visibility.go`) — correct, do not change.
- Transport authorization: `internal/transport/internalmethods.go`
  `LocalOnlyMethods` — the dispatcher refuses these methods for

## Intent

Five surfaces, one packet:

1. **§6.1 `WorkflowsSection.svelte`** — per-project sidebar section
   mounted from `ProjectItem.svelte` below the project's thread list;
   hidden entirely for projects with no workflows and no listed runs.
   Header row (chevron + uppercase "Workflows") with the roll-up rules
   of §6.1; expanded run rows with the restricted signal vocabulary,
   ordering needs-you (oldest first) → failed → running → queued →
   done. Row click → `openWorkflowsPane` at that run (full stack); the
   row matching the pane's current run gets the active highlight. No
   drag, no context menu.
2. **§6.2 `WorkflowsFooter.svelte`** — always-visible row in
   `Sidebar.svelte` directly above `SettingsFooter.svelte`: icon +
   "Workflows" + global attention count (amber, only when > 0). Click →
   workflows pane at overview.
3. **§6.3 thread-mode exclusions** — workflow/workflow-studio/
   workflow-triage threads must never appear in normal thread lists,
   pickers, or search. Backend listings already exclude them; verify
   and close the CLIENT-side leak paths (live `thread:updated`/created
   ingestion into sidebar lists, `UnifiedThreadPicker`, sidebar
   search), principled by mode — never by title convention. Widen the
   `Thread.mode` union in `types/models.ts` if P3.1 didn't already.
   Once opened from a workflow surface they behave as normal thread
   panes — exclusion applies to listings only, never to opening.
4. **§10 notification deep links** — widen the activation queue to the
   two workflow target kinds and route them: `workflow-item` → the
   workflows pane at that run inside the sweep; `workflow-triage-agent`
   → the project's triage agent thread in a pane. Hydration gating
   (queue until `markNotificationHydrated`) unchanged.
5. **§5.7 + §12** — an "Open full review" affordance in run detail that
   opens the REAL review companion (no parallel diff renderer), and the
   remote view-only posture: reads reclassified wire-safe, a
   server-derived locality flag in the bootstrap manifest, and every
   mutating workflow affordance disabled remotely with title
   "Local only".

Automation-driven chrome (Scheduled section, next-run banner, Run now,
enable/disable) is OUT of scope — M5 populates it; render nothing for
it now (§13 non-goals apply).

## Binding decisions (do not re-litigate; verify cited facts before relying on them)

1. **Sidebar data store.** New always-on
   `stores/workflowsSidebar.svelte.ts` — the workflows pane store
   deactivates and empties when the pane closes, so the sidebar/footer
   must NOT read it. The sidebar store holds run summaries + the
   per-(projectId, workflowId) definition metadata it needs, fetched
   with the same per-project load helpers the pane uses
   (`workflowData.ts`) — do not duplicate merge logic. Initial fetch
   once at app boot after projects hydrate; `eventsWorkflow.ts` routes
   item-state/phase-state/queue events to this store IN ADDITION to the
   pane store (fan-out at the events layer, no cross-store imports from
   the pane store). Definitions are fetched only for projects that have
   listed runs (phaseCount for the running row); items via
   `WorkflowListItems("")`. Initialization is owned by the sidebar
   components' mount (`WorkflowsFooter` is always rendered — its mount
   triggers the one-time fetch, idempotently); `App.svelte` is not in
   the allowlist and must not be touched.
2. **Sidebar membership** = runs that are NOT cancelled and NOT
   (done with non-empty disposition). Resolved runs drop off; done
   awaiting disposition stays as dim `done`. This is the same
   parked/resolved vocabulary as the sweep — reuse
   `parseWorkflowDisposition`/`isWorkflowParked`, do not re-derive.
3. **Attention counts** (section roll-up amber count AND footer badge)
   = needs-human + failed only. Done-awaiting-disposition is NEUTRAL
   here (R1: it never alarms; it rides the drain summary). Quiet →
   §11: section collapses to hint-toned header + neutral count, footer
   shows no count.
4. **Running row progress.** `2/5 · 14m` renders when the current
   phase index is known (from the latest `workflow:phase-state` event
   this session, resolved against the catalog's phase list) — after a
   reload with no events yet, degrade to elapsed-only (`running · 14m`)
   until the next phase event. Do NOT fetch `WorkflowGetItem` per
   sidebar row to recover the phase index (N+1 fetch storm; principle
   4). Elapsed ticks may piggyback on whatever coarse re-render the
   row already gets — no per-second timers.
5. **§6.3 exclusion helper.** One frontend helper
   (`utils/threadModes.ts` or the existing module if one fits:
   `isHiddenThreadMode(mode)`) mirroring `threadmode.go` hiddenModes,
   applied at the client-side list/picker/search boundaries. First
   VERIFY which paths actually leak (create a workflow-mode thread via
   the harness or trace `thread:updated` ingestion) and report the
   findings; add the guard to real leak paths plus the
   picker/search/list build sites as defense-in-depth.
6. **§10 routing.** `NotificationTarget` widens to
   `'thread' | 'workflow-item' | 'workflow-triage-agent' | 'none'`
   with optional `workItemId`/`projectId`, validated at the events.ts
   parse boundary mirroring Go's `ValidateTarget` (exactly one
   identifier per kind; length caps). `workflow-item`: resolve via
   `WorkflowGetItem(workItemId)`; success → `openWorkflowsPane({kind:
   'sweep-at-run', ...})` (per §10 "inside the sweep"); resolve failure
   (dead run — match the pane restore's 'no rows in result set'
   handling) → error toast + workflows pane at overview.
   `workflow-triage-agent`: `WorkflowOpenTriageAgent(projectId)` →
   `GetThread` → open in a pane (same wire→Thread conversion the
   workflow components use). Extend `notificationActivationQueue.ts`'s
   dependency object rather than importing stores into it (it is
   deliberately store-free; `eventsNotification.ts` binds the real
   deps).
7. **§5.7 review affordance.** In `WorkflowRunDetail.svelte`, for
   `reason === 'gate'` and `state === 'done'` (the states that render
   Changes), an "Open full review" affordance opens the review
   companion with `sourcePaneId = WORKFLOWS_PANE_ID` and the run's
   newest phase thread (same reverse-find-first-threadId selection the
   diff evidence uses). Read `companionPanes.svelte.ts`,
   `reviewPane.svelte.ts`, and `PaneHost.svelte`'s companion branch
   FIRST. Small seams to make a non-thread source pane work (e.g. the
   companion's source-pane lookup) are in scope; if the companion
   machinery structurally assumes a ThreadPane source such that clean
   integration needs real surgery, that is BLOCKED — do NOT build a
   parallel review surface (§5.7 bans it) and do NOT special-case a
   fake thread pane.
8. **§12 reclassification (backend).** Move EXACTLY these five reads
   out of `LocalOnlyMethods` and into `wireSafeMethods`
   (`methods_gen_test.go`): `WorkflowListItems`, `WorkflowGetItem`,
   `WorkflowListItemCosts`, `WorkflowListDefinitions`,
   `WorkflowGetJobNotes`. Every other workflow method — all mutations,
   `WorkflowSetJobNotes`, and every thread-opening/creating RPC
   (`WorkflowOpenTriageThread`, `WorkflowOpenTriageAgent`,
   `WorkflowOpenStudioThread`, `WorkflowCompleteTakeover`) — stays
   LocalOnly. `GetBranchBaseDiff` STAYS LocalOnly (it predates
   workflows and its surface is app-wide; remote run detail renders
   the diff section as a disabled "Local only" affordance instead).
   Update the comment block in `internalmethods.go` to state the
   read/mutate split. Verify the workflow event payloads carry nothing
   beyond what these newly wire-safe reads return, and note the result
   in the report.
9. **§12 locality flag (backend).** `Bootstrap` in
   `internal/transport/server.go` gains `Remote bool`
   (`json:"remote,omitempty"`), derived per-request in
   `handleBootstrap` from the SAME peer-locality predicate
   `ResolveForOrigin`/the WS upgrade path uses to gate LocalOnly
   methods — find that predicate and share it; the flag and the
   enforcement MUST NOT be able to disagree. Loopback peers get no
   field (embedded webview unchanged).
10. **§12 view-only signal (frontend).** One helper (in
    `transport/runMode.ts` or a sibling module) —
    `isViewOnlySession(): boolean` — true when the bootstrap manifest
    carried `remote: true`. Verify how the `--connect` client obtains
    its manifest (`clientmode.go` injection vs fetching the remote
    server's `/bootstrap.json` per `wsClient.ts`) and make sure the
    flag flows on that path too — a `--connect` client attached to a
    non-loopback server is view-only for workflows (its LocalOnly
    calls are refused server-side); a `--connect` to a loopback URL is
    not. If clientmode's injected bootstrap needs the field plumbed
    through, that is in scope.
11. **§12 view-only rendering.** When `isViewOnlySession()`: every
    mutating workflow affordance renders disabled with
    `title="Local only"` — queue toggle, drag reorder (draggable off,
    grip hidden), "+ New run"/intake, "+ New workflow"/Edit (studio),
    Triage, all action-row buttons, queue-strip cancel/remove,
    JobNotes editing, discard, and the diff Load-changes/retry
    buttons (GetBranchBaseDiff is LocalOnly). Navigation — levels,
    breadcrumbs, sweep browsing (j/k), opening nothing that creates
    threads — stays live. Do not fork view-only component variants;
    disable in place. The sidebar section/footer render normally
    (reads are wire-safe now).
12. **No bindings regeneration expected.** This packet changes no
    bound method signatures; `frontend/bindings/**` should be
    untouched. If you believe a regeneration is needed, treat it as a
    scope question (BLOCKED), not a convenience.
