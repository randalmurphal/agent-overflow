## Intent

Wire OS notifications end to end as a reusable pipe on EVERY supported
platform path, including the real Windows/WSL split:

1. **In-process path (Linux/macOS desktop, `runDesktop`):** register the
   Wails v3 notifications service; request authorization ASYNCHRONOUSLY;
   one internal Go send helper with a typed deep-link target; activation
   (click) emits ONE event the frontend consumes. Dismissal is NOT
   activation.
2. **Windows/WSL bridge path:** the backend runs `-tags nogui` inside WSL
   and has no Wails application; the native launcher
   (`cmd/agent-overflow-windows`) is the Wails process. The backend's send
   helper publishes over the existing HTTP+WS transport; the launcher
   subscribes, presents via its own notifications service, and posts
   activations back as a wire RPC; the backend then emits the same
   frontend event as the in-process path.
3. **Degraded path (headless, harness, WSL without the launcher, no
   daemon):** app starts normally, the condition is logged once, the send
   helper returns a visible typed error. Never a crash, never a silent
   no-op, never a blocked startup. `--harness` keeps working untouched.

The workflows system (M3) sends through this pipe; this packet delivers
the pipe only — no workflow-specific anything, no notification
preferences/throttling UI.

## Design decisions (binding)

- **Target type:** `NotificationTarget{ Kind string ("thread"|"none"),
  ThreadID string (omitempty) }` riding in notification user data,
  unchanged from rev1.
- **Send helper:** ONE internal unexported method on `*App`
  (`notifyOS(title, body string, target NotificationTarget) error`) that
  routes by build/runtime mode: in-process service when the Wails app owns
  notifications; transport publish when running headless with a connected
  launcher; typed visible error otherwise. Callers never know which path
  ran.
- **Async authorization:** authorization is requested on a goroutine after
  service startup (both in the desktop build and in the launcher). Until
  it resolves, `notifyOS`/launcher-send fails with a typed
  "authorization pending" error; denial parks the service in a visible
  unavailable state. Service startup MUST NOT block on authorization
  (macOS can take up to 180s).
- **Activation event:** one new channel `notification:activated`, payload
  = the target object, added via the documented add-a-channel path (no
  generic passthrough). Emitted by the backend in BOTH paths (in-process
  callback, or launcher RPC → backend emit) so the frontend sees one
  surface.
- **Dismissal:** with the prerequisite fork fix, a dismiss produces NO
  `notification:activated` event on any platform. Encode this expectation
  in a unit test at whatever seam the adapter exposes (e.g., the response
  handler ignores non-activation identifiers) — do not re-test the fork
  itself.
- **Windows bridge, backend side:** `notifyOS` in headless mode publishes
  channel `notification:send` (payload: id, title, body, target) through
  the same event ring every other channel uses. Add the channel via the
  documented path. If no launcher client is subscribed, sends still return
  nil at the helper level only when the transport accepted the publish —
  presentation is best-effort by design; log the no-subscriber condition
  once. (The SPA never subscribes to `notification:send`.)
- **Windows bridge, launcher side:** the launcher already holds
  `{port, token}` from the bootstrap line. Add a minimal Go WS client
  (living beside the launcher code it serves — `cmd/agent-overflow-windows`
  or `internal/wsllauncher`, your call, stated in the report) that:
  subscribes to `notification:send`; presents via the launcher's Wails
  notifications service (registered + async-authorized as above); on
  activation calls the new bound RPC `NotificationActivated(target)`;
  reconnects with bounded backoff while the backend process is alive; and
  never crashes the launcher on WS errors (log to `launcher.log`).
  Windows-only build tags keep this out of the Linux/macOS binaries.
- **`NotificationActivated` bound method:** on `*App`, registered through
  methodgen + bindings regen, classified in `LocalOnlyMethods` (it
  synthesizes UI navigation; remote browser clients must not drive it).
  It validates the target shape and emits `notification:activated`.
- **Frontend handling:** subscribe `notification:activated` where other
  server-push events are wired. `kind === "thread"` with a known thread →
  focus/open that pane via the existing store affordance. Unknown thread
  or `kind === "none"` → one console-visible log line. **Pending
  activation queue:** activations arriving before the thread registry /
  pane layout hydrate go into a bounded FIFO (cap 8, drop-oldest, log on
  drop) that drains once hydration completes — a cold-start activation
  must not be treated as unknown. Cover the queue with a vitest store
  test (pre-hydration arrival → drains post-hydration; overflow drops
  oldest).
- **`HarnessNotify` (Harness receiver):** calls the same send helper
  (error surfaced in the RPC response) and ALSO synthesizes an activation
  of the same target so e2e asserts the full frontend path without OS
  interaction. Make it explicit in code that the synthetic activation
  bypasses only the OS layer. Regen methodgen + TS bindings.
- **e2e:** one spec file following `e2e/AGENTS.md` (never sleep):
  `HarnessNotify` with a seeded thread target → frontend receives
  `notification:activated` and the pane-focus behavior happens; a `none`
  target → the logged no-op path. The harness runs headless — the spec
  exercises the degraded send path plus the synthetic activation, and
  that is the honest claim to make in the report.
- **Verification honesty:** OS-level presentation and click-through on
  real Windows/WSL and real macOS/Linux desktops CANNOT be verified in
  your environment. The launcher bridge's WS client IS unit-testable
  (subscribe/reconnect/RPC against a stub transport server) — do that;
  state the OS-presentation surfaces as explicitly unverified,
  user-assisted verification required.
