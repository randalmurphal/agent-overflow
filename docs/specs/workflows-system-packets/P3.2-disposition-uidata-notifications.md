## Intent

Backend for the M3 human surface's outcomes and data, in two halves:

**Half A — disposition (D3.3, amends WHAT-spec §9):**

1. Manual disposition RPCs on done items: merge to the base branch,
   create a PR, discard the worktree (existing guarded removal). Never
   forced, never silent: any conflict or dirty base refuses and parks
   `needs-human(disposition)`.
2. Profile-driven auto disposition: `disposition: manual | auto-pr |
   auto-merge` (default `manual`, already in the profile shape per D6) —
   `auto-*` runs the same machinery automatically when an item reaches
   `done`, only from a green terminal state and only on a clean merge;
   refusal parks `needs-human(disposition)` exactly like manual.
3. Durable receipts (sha, mode, policy, PR ref, timestamp) persisted on
   the work item and readable from the run-detail RPC.
4. D6 cleanup interaction: `cleanup: auto` for writing workflows takes
   effect only after a successful disposition (auto-pr / auto-merge
   landed); an unlanded branch is never silently discarded.

**Half B — UI data + notification senders:**

5. Per-item OS notifications (run entered `needs-human` any reason, or
   `failed`) and a coalesced drain summary (on drain-to-empty and on
   pause) through the P0.3 pipe, with typed deep-link targets.
   Done-awaiting-disposition alone does NOT notify (UI-SPEC §10 / R1);
   it rides the drain summary.
6. D4.3 digest ("WHAT HAPPENED / WHAT IT NEEDS") fields on run detail.
7. D12 continuity-notes read/write RPCs over the existing
   `automations.notes` column.
8. Intake support: a workflow-listing RPC with dry-run validation status
   and predicted queue position (UI-SPEC §7; D4.1 gap 6 — broken
   definitions listed with their first validation error, enqueue blocked
   upstream by the UI).
9. `WorkflowRemoveQueuedItem(itemID)` (P2.2 carry-forward).
10. Fire-and-forget enqueue (P2.6 carry-forward): stop attaching
    runner-start provisioning futures to the enqueue/set-queue command
    responses; start failures ride the existing `workflow:error` /
    `workflow:item-state` events.

No UI (`frontend/src/**` untouched). No scheduler/automation triggers
(M5). No studio or first-party MCP tools (M4). No notification
presentation or bridge changes.

## Binding design decisions

1. **Three disposition RPCs, all LocalOnly:** `WorkflowMergeItem(itemID)`,
   `WorkflowCreateItemPR(itemID)`, `WorkflowDiscardItem(itemID)`. Add all
   new bound methods from this packet to the existing `Workflow*` block in
   `internal/transport/internalmethods.go` (same comment style), extend
   the `privilegedApp` fixture stubs in `dispatcher_test.go` exactly as
   the exhaustive classification tests require, and regenerate
   `methods_gen.go`. Classification test expectations stay untouched.
2. **Merge machinery reuses `internal/git`** (`core.go`, `mergetree.go`,
   `actions.go` are the exemplars; PR creation goes through the existing
   forge layer in `forge.go`/`github.go`/`gitlab.go`). Merge runs at the
   project root against the profile's base branch: fast-forward when
   possible, else a merge commit — record which in the receipt. Refuse
   (park, receipt-less) when: the base working tree is dirty, the merge
   does not apply cleanly, or the item's branch/worktree is missing.
   NEVER `--force*`, never `checkout -f`, never touch stashes you did not
   create. A refusal parks `needs-human(disposition)` via the engine
   (typed reason exists in the v25 CHECK) and the park emits the same
   `workflow:item-state` shape as every other park.
3. **Disposition validity:** merge/PR valid only from `done`. Discard
   valid from `done`, `failed`, `cancelled`, and `needs-human` — it routes
   through the EXISTING guarded worktree removal (P2.6) and does not
   invent a second deletion path. Auto policies fire only on the
   `done` transition inside the engine drain (app-level hook on the same
   emit seam the notification senders use is also acceptable — document
   which and why); manual RPCs are user calls. Both paths share one
   implementation.
4. **Receipts + digest persist on the item row — migration v26**, via
   `ALTER TABLE work_items ADD COLUMN` twice: `disposition TEXT NOT NULL
   DEFAULT '' CHECK(disposition = '' OR json_valid(disposition))` and
   `digest TEXT NOT NULL DEFAULT '' CHECK(digest = '' OR
   json_valid(digest))`. If SQLite rejects a CHECK on ADD COLUMN in
   practice, fall back to the established rebuild pattern — verify, don't
   assume; extend the migration tests the way
   `TestMigrationV25AddsWorkflowModesTakeoverAndTriageLink` asserts
   columns and preservation. Receipt JSON shape (document it in the
   report): `{action: "merged"|"pr"|"discarded", mode: "ff"|"merge",
   sha, prRef, policy: "manual"|"auto-pr"|"auto-merge", at}` — omit
   fields that don't apply. `WorkflowGetItem` returns both receipt and
   digest.
5. **Digest generation must never block or fail a park.** On entering
   `needs-human` or `failed`, synchronously persist a deterministic
   template digest derived from state/reason/envelope (question text,
   gate phase, check names, error class — same no-internals rule as the
   P3.1 triage seed), then asynchronously upgrade it via the existing
   `internal/textgen` infrastructure (the `threadtitle`/`commitmsg`
   precedent: bounded prompt, structured output, deadline, both-provider
   fallback). Async failure keeps the template silently-in-logs (log it,
   keep the template); success updates the row and re-emits
   `workflow:item-state` so the UI refreshes. Do not generate digests for
   `done` without disposition-park or for `queued`/`running`.
6. **Notification senders hook the app emit seam, not engine internals.**
   Per-item: title = run title (item goal, bounded), body = the digest's
   one-line "what it needs" (template version — never wait for the
   upgrade). Extend `internal/notify.Target` additively:
   `Kind` gains `workflow-item` (new field `WorkItemID`) and
   `workflow-triage-agent` (new field `ProjectID`), each with byte caps
   mirroring `MaxThreadIDBytes`; update `ValidateTarget`,
   `TargetToMap`/`TargetFromMap`, and the notify package tests. The
   launcher bridge and desktop paths carry Target opaquely — verify with
   the existing tests, change nothing there. Frontend activation ROUTING
   for the new kinds is P3.4/P3.6's job; this packet only guarantees the
   wire shape round-trips.
7. **Drain summary coalescing:** one notification per drain, fired when
   the queue transitions to empty-and-idle (and on pause with items still
   pending), summarizing outcomes since the last summary or queue start:
   "N finished · N need you · N failed" (omit zero segments). Target =
   `workflow-triage-agent` for the project. Track the tally in the app
   layer keyed by project; a process restart may reset the tally
   (document as an assumption) — do not persist a new table for it.
8. **Continuity notes:** `WorkflowGetJobNotes(automationID)` /
   `WorkflowSetJobNotes(automationID, notes)` over `automations.notes`
   (column exists — v23). Size-cap writes (64 KiB, mirroring the notify
   body cap) and reject unknown automation ids. Both LocalOnly. Seed-time
   injection and the `update-job-notes` tool are M5/M4 — NOT here.
9. **Intake listing:** `WorkflowListDefinitions(projectID)` returns, per
   resolvable workflow (project + shared scopes): id, name, scope,
   phase count and per-phase {id, provider, model}, step-mode default,
   validity + first validation error (from the existing dry-run
   validator), and whether every referenced check/resource/command binds
   in the project profile (the D1 cross-check — reuse it, don't
   reimplement). Include `predictedQueuePosition`: where a new enqueue
   would land given current queued items. LocalOnly.
10. **`WorkflowRemoveQueuedItem(itemID)`:** valid only while `queued`;
    engine command transitions the item to `cancelled` (record kept, no
    worktree exists yet to clean), emits `workflow:item-state`, and the
    queue re-sorts. Racing a drain start loses politely: if the item
    started, return the invalid-state error — never stop a started run.
11. **Fire-and-forget enqueue:** `WorkflowEnqueueItem` and
    `WorkflowSetQueue` (and `UpdateQueueSettings`) stop blocking on
    runner-start provisioning futures. The engine command still validates
    and persists synchronously (the RPC still returns the created item /
    an immediate validation error); only the starts it TRIGGERS detach.
    Keep `engine.Sync()` semantics intact for tests. Start failures
    surface exactly as they already do from mid-run starts
    (`workflow:error` + item-state park) — assert this with a test that
    fails provisioning after a fire-and-forget enqueue. Resume, answer,
    and gate-resolve keep their current synchronous contracts (their UI
    flows depend on errors returning inline).
