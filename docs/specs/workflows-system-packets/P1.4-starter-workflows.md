## Intent

Three tightly-related deliverables that finish M1:

1. **Starter workflow content** (D1 "starter workflows"): `build-and-validate`,
   `multi-lens-review`, and `poll-jira-and-start` as complete, validator-clean
   definition sets (YAML + sibling prompt .md files), embedded in the binary
   as scaffold sources.
2. **`ao workflow new`**: scaffolds a starter (or a minimal blank skeleton)
   into a target scope directory.
3. **Profile-backed validation**: `ao workflow validate`/`list` with
   `--project <slug>` now load that project's `profile.yaml` (P1.2, merged)
   and pass it to `def.Validate` as bindings — `unchecked` remains only for
   the genuinely profile-less cases.

## Binding design decisions

- **Content embedding:** starter definitions + prompts live under
  `internal/workflow/starters/` as real files, `go:embed`-ed, exposed by a
  small accessor (list + fetch). They are SOURCES for scaffolding — the
  engine never reads them directly (D1: scaffolds, not a hidden tier).
- **Starter quality bar:** each starter must (a) pass `def.Validate` with
  nil bindings apart from binding checks, (b) declare its check/command/
  capacity names and document them in a leading YAML comment block so a
  user/agent knows what their profile must bind, (c) carry prompts written
  for real use — envelope-aware (the D2 status contract), untrusted seed
  content fenced in delimited blocks (D2 failure mode 9), no placeholder
  lorem text. Content is reviewed as product surface, not filler.
- **CI-anchored validity:** a Go test iterates every embedded starter and
  asserts `def.Validate` returns zero findings (bindability via a test-local
  Bindings stub that binds exactly the names the starter documents. A
  documented-name/used-name mismatch must fail the test).
- **`ao workflow new <starter|blank> --id <new-id>`:** copies the starter
  set (or a minimal valid skeleton for `blank`) into the target scope dir
  (`--project <slug>` → project scope, else shared), rewrites the `id:`
  field to `--id`, refuses to overwrite existing files (distinct error,
  exit 2), prints the created paths, and runs `def.Validate` on the result
  (surfacing findings exactly like `ao workflow validate`). `--json`
  variant per the existing aocli conventions.
- **Profile-backed validation:** when `--project` is given, load
  `<config-root>/projects/<slug>/profile.yaml` via `internal/workflow/
  profile`. Loaded profile → pass as `def.Bindings`; absent profile →
  current `unchecked` behavior; malformed profile → operational error
  (exit 2) that names the profile path — never silently fall back to
  unchecked.
- House style: extend `internal/aocli` following its AGENTS.md; keep files
  under ~500 lines; all errors typed/loud per repo rules.

## Out of scope / forbidden

- MUST NOT touch: `internal/workflow/def/**` and
  `internal/workflow/profile/**` are read-only dependencies — if starter
  content cannot validate without changing them, that is a BLOCKED with the
  exact finding, not permission to edit them. Also forbidden:
  `internal/store/**`, `internal/transport/**`, any `app*.go` / `main*.go`,
  `frontend/**`, `Makefile`.
- MUST NOT implement scheduler/automation triggers, engine execution, or
  any `ao run` surface.
- MUST NOT hardcode `jira`/`acli`/`gh` binaries inside workflow YAML —
  command NAMES bound by profile only (prompts may mention what a command
  conventionally does).
