## Intent

Writing work items get real isolation: one worktree + branch per item, cut
from the profile base branch at start, with profile setup hooks run before
the first phase. Read-only workflows (derived, never declared) keep running
against the project root and pay nothing. Step mode gives new workflows a
trust-building park at every gate. Workflow-level artifact outputs are
captured into the app-managed store at the producing phase's completion so
deliverables survive worktree discard.

Out of scope: disposition (merge / PR / discard — M3 per the milestone plan),
cleanup EXECUTION for writing workflows (gated on disposition; see below),
fan-out sub-worktrees and per-phase access→sandbox mapping (deferred with the
tool-driver packet), harness `workflows:` seeding (P2.7), all UI.

## Binding design decisions

### Provisioning is runner-owned, never engine-goroutine work

Worktree creation and setup hooks can take minutes (`pnpm install`). They
MUST NOT run on the engine command goroutine (its AGENTS.md invariants
stand). Provisioning happens in `Runner.Start` of an item's FIRST phase
attempt, before the thread/turn work:

- `def.DeriveWorkspaceNeed(request.Workflow)` == project-root → no worktree;
  the phase thread's workspace is the project root (today's behavior).
- Worktree need, item fields empty → provision now: branch cut from the
  profile's `base_branch` (fall back to the repo's current default the way
  `PrepareThreadWorktree` resolves it), worktree at the
  `defaultWorktreePath`-convention location, branch named via the existing
  generated-branch-name helpers with a workflow-recognizable prefix. Then
  run setup hooks (below). Then persist the three item fields via a new
  store method (`UpdateWorkItemWorkspace(itemID, worktreePath, branch,
  baseBranch)` — columns exist). Creation failure rolls back the worktree
  (match `PrepareThreadWorktree`'s rollback discipline).
- Worktree need, item fields already set (resume / crash restart / later
  phases): reuse; if the worktree directory no longer exists, that is a
  setup failure (park — the human decides; never silently re-cut the
  branch).
- Phase threads of a worktree-backed item get the worktree as
  `WorkspacePath`.

### Typed setup-failure error (small additive engine change)

`Runner.Start` errors currently park `agent-error`. Provisioning/setup
failures are not agent failures: introduce a sentinel the engine
recognizes (e.g. `engine.ErrSetupFailed` wrapped via `%w`) and have the
startRunner error path park `needs-human(setup-failed)` when the error
matches, `agent-error` otherwise. No other FSM change.

### Setup hooks (profile `worktree_setup`)

- Execute after worktree creation, before the first phase turn: `copy`
  entries (project-root-relative → same relative path in the worktree,
  using the confinement rules the profile package already validated), then
  `run` argv commands sequentially in the worktree.
- `profile.WorktreeSetup` gains `Timeout Duration` (additive; default 10m)
  covering the whole run sequence — config-driven per the harness
  obligation, no hardcoded waits. Timeout or non-zero exit → setup-failed
  park with the command and output tail in the error.
- Hooks run once per item at provisioning, not per phase.

### Step mode (park at every gate)

- Migration **v24** (append-only, authorized): `work_items` gains
  `step_mode INTEGER NOT NULL DEFAULT 0`. Store struct/scan/create updated.
- `WorkflowEnqueueItem` gains a `stepMode bool` parameter (bindings regen;
  registration-list + LocalOnlyMethods updates are the documented path).
- Engine: on a step-mode item, when gate evaluation yields an automatic
  decision (advance / loop / done / failed), do NOT execute it — persist
  the trace with that decision as usual and park `needs-human(gate)`. The
  phase row keeps the real evaluated decision; nothing is rewritten.
- Resolution: `WorkflowResolveGate` approve on a step-parked item records
  the intervention and executes the recorded decision (the existing
  persisted-decision continuation machinery in `human.go` is the natural
  home — extend, don't fork). Reject returns an error naming the
  alternatives ("step gates support approve; use cancel, resume, or take
  over") — a step gate has no reject route by construction. Human-routed
  gate decisions (`DecisionHuman`) behave exactly as before.
- Crash between step-park and approve must recover through the existing
  rebuild path (the persisted trace + parked status already encode
  everything; add the rebuild test).

### Artifact capture (D13, v1 slice)

- `def.WorkflowOutput` gains `Artifact bool` (additive field + authoring
  schema): true marks file deliverables; false/absent means a plain value
  (nothing to copy; values remain derivable from envelopes).
- At a phase attempt's successful completion (status done), the runner
  copies each workflow output whose `From` resolves to one of THIS phase's
  output variables and is marked `artifact`: the variable's value is a
  workspace-relative file path (validate confinement against the phase
  workspace; reject absolute/escaping paths), copied to
  `<data-root>/workflow-runs/<item-id>/artifacts/<output-name>` preserving
  the source extension. (This intentionally uses the established
  `workflow-runs/<item-id>/` root from P2.4's narratives rather than D13's
  illustrative `runs/<run-id>/` path — note the deviation in your report.)
- Copy failure must not rewrite the phase outcome: emit a `workflow:error`
  event naming the output and keep going. The engine's envelope authority
  is untouched.
- No new store table: artifacts live on disk at the deterministic path;
  `WorkflowGetItem` gains an artifacts listing (name, path, size, mtime)
  derived from that directory.

### Cleanup policy (plumbing only in v1)

`def.Workflow.Cleanup` (`auto` | `manual`, default manual) is already
parsed/validated. v1 semantics: read-only workflows have nothing to clean
(inert); for writing workflows `auto` is gated on disposition landing (M3)
and therefore executes nothing yet. Document this state on the field and in
the engine/runner guide you touch — do NOT implement terminal-state worktree
discard in this packet.

## Invariants

- The engine command goroutine never performs git operations, hook
  execution, or file copies.
- Derived need is the only isolation trigger — no declared "worktree: true".
- An unlanded branch is never silently discarded; no cleanup execution for
  writing workflows in this packet.
- Step mode preserves the genuinely evaluated gate decision in the trace;
  approve executes exactly that decision.
- Artifact capture failure never alters a phase outcome or envelope.
- Worktree layout/branch naming follow the existing `app_worktree.go` +
  `internal/git` conventions — one layout, not two.
- Errors are user-facing state, not log entries.
