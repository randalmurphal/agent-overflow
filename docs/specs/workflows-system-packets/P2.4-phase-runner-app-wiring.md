## Intent

Connect the engine (P2.2) to real provider execution (P2.3) and to the app:
implement `engine.Runner` on top of workflow-mode threads, construct and start
the engine in the app lifecycle, expose the control-plane bound methods over
the transport, and add the two workflow settings. After this packet a work
item enqueued through a bound method runs its phases end-to-end against a
provider, parks on gates/questions, and survives an app restart via the P2.2
crash sweep.

**In scope only for agent-driver, single-shape phases.** Tool-driver phases
(`driver: tool`) and fan-out/join shapes are later packets — `Runner.Start`
must reject them with a clear error (the engine parks the item agent-error).
Watchdog, retry backoff, budgets (P2.5) and worktree-per-run, setup hooks,
env/secret delivery into sessions, derived read-only, step mode (P2.6) are
all out of scope.

## Binding design decisions

### Threads and sessions

- **One workflow-mode thread per phase attempt.** `Runner.Start` creates a
  thread with `mode='workflow'` directly via the store (the discussion
  precedent — `threadmode.ValidateCreate` must NOT learn 'workflow'; document
  the exclusion where 'discussion' is documented). Workspace is the project
  root (worktrees are P2.6). Workflow threads must be excluded from normal
  thread listings the same principled way discussion threads are.
- **Provider/model come from the phase** (`def.Phase.Provider`, `.Model`).
  Reuse the existing thread model-profile machinery; do not invent a second
  model-resolution path. Runtime mode is `full-access` — workflow phases run
  autonomously; human control is gates, not tool approvals.
- **Schema attachment is a session invariant, not a one-shot.** The phase's
  `def.EnvelopeSchema` must reach `claude.Config.OutputSchema` at every spawn
  of that thread's session (including restarts/resumes) and
  `SendOptions.OutputSchema` on every schemaed codex turn. A workflow thread's
  session must never start without its phase schema.
- **Turn observation** goes through `subscribeThreadTurnObserver` (P0.1).
  Observers registered before the send; unsubscribed at outcome delivery.
  Session/turn failure signals (send error, session death, turn error) map to
  `Outcome{Kind: OutcomeExecutionFailure}` — never a silent hang.

### Envelope handling (spec §10/§12)

- On `EventTurnComplete`, take `ProviderEvent.StructuredOutput` and run
  `def.ValidateEnvelope(phase, payload)` (def's size cap). That validation is
  the ONLY success authority — provider error flags and turn status are
  advisory.
- Valid envelope → `Outcome{Kind}` from envelope status (`done` | `question` |
  `stuck`).
- Absent-or-invalid → exactly ONE feedback turn on the same thread (validation
  findings in the message, schema attached as always), then, if still
  absent-or-invalid, `OutcomeExecutionFailure` (engine parks agent-error).
  The retry counter is per phase attempt, in-memory on the runner.

### Narrative (spec §3)

- System-dictated path, one per phase attempt, under the app-managed data
  root the store already uses (do not invent a second root):
  `workflow-runs/<item-id>/<phase-id>.<attempt>/narrative.md`. The runner
  creates the directory, instructs the agent in the prompt suffix to write its
  narrative there, and attaches the path to the run record whether or not the
  agent writes the file.
- New store method on `work_item_phases.go` (columns already exist):
  `AttachWorkItemPhaseRun(itemID, phaseID string, attempt int, threadID,
  narrativePath string) error`, called once per attempt when the thread is
  created. Store-level test alongside the existing ones.

### Prompt assembly

- Body: `RunRequest.Phase.Prompt` — after Scope amendment 1, the snapshot
  carries inlined prompt BODIES, not file paths — interpolated via
  `def.Interpolate` with the engine's `RunRequest.Vars` (the definitions own
  their `<untrusted-*>` fencing; the runner does not add fencing of its own).
- System-owned suffix (identical shape across providers, exact wording yours):
  narrative instruction (absolute path + purpose), then a feedback block only
  when `RunRequest.Feedback` is present (note + values, values rendered as
  fenced JSON), then one short envelope reminder (final message must satisfy
  the attached schema; status is done | question | stuck).
- Pure helpers (prompt suffix assembly, narrative path building, envelope →
  outcome mapping, validation-findings → retry message) live in a new
  `internal/workflow/runner/` package with unit tests; everything touching
  App state (threads, sessions, store, observers) stays in main-package
  `app_workflow_runner.go`. Add the package to `internal/AGENTS.md` and give
  it an `AGENTS.md` + `CLAUDE.md` symlink per house rules.

### Question answering (additive engine extension; spec §7)

- New engine command `Answer(itemID, answer string) error` on the same
  request/reply channel as the other commands. Valid only for
  `needs-human` items with reason `question`; empty answer rejected; answer
  capped at the same 16KiB as human-gate notes; full-concurrency behaves like
  `Resume` (error). It loads the parked item, creates the next phase attempt
  whose `InputEnvelope` carries `Feedback{Note: answer}`, transitions to
  running, and starts the runner.
- `RunRequest` gains `PriorThreadID string`, set ONLY on answer-initiated
  attempts, resolved by the engine from the parked attempt's persisted
  `ThreadID`. When `PriorThreadID` is set, the runner does NOT create a new
  thread: it sends the answer as the next turn on that thread (same session
  context, schema attached — spec §7's "same session, same schema"). All
  other attempts (initial, gate loop-backs, resumes) get a fresh thread.
- The extension must be additive: no reworking of existing FSM transitions,
  teardown, or drain paths. Engine `AGENTS.md` gains the Answer contract.

### Runner.Stop contract

- `Stop(ctx, RunKey)` for an unknown key returns `(nil, nil)` — the P2.2
  crash sweep calls Stop for attempts this process never started, and that
  must be a no-op, not an error. For a known key: interrupt the in-flight
  turn via the existing per-provider interrupt path, release runner-local
  state, return `(nil, nil)` (no partial-envelope recovery in v1 — document
  that the return slot exists for it).

### App wiring

- `NewApp`-adjacent construction: `engine.New(...)` with the store, the
  runner, an Emitter that forwards to the app's transport-aware emit path
  (replay-mirrored, per how-to §Add a New Routing Channel — the event names
  and payload structs already exist in `engine/types.go`), a
  DefinitionSource resolving `store.WorkItem{WorkflowID, WorkflowScope}`
  through the same discovery/resolution `internal/aocli` uses (extract shared
  code if needed rather than duplicating it) and inlining prompt bodies via
  `def.InlinePrompts` (Scope amendment 1), and a ProfileSource wrapping
  `internal/workflow/profile` loading. Engine `Start` runs where other
  startup services start (after the store is open); `Close` joins the
  existing shutdown path. Engine construction failure or `Start` failure is
  loud (user-visible error state, not a log line).
- Frontend subscription to `workflow:*` channels is M3 — Go-side emission
  only in this packet.
- Settings: `Settings` gains `WorkflowQueueActive bool` (default true) and
  `WorkflowConcurrency int` (default 2, valid 1–32), with the same
  defaulting/validation treatment neighboring fields get. They feed
  `engine.Config` at construction. A live settings update forwards via
  `SetQueue`; extend `SetQueue(active bool, maxStarts int)` to also carry
  concurrency so the running engine picks it up without restart (the drain
  loop already re-reads its config each pass; keep the change minimal and
  single-goroutine-safe).

### Bound methods (all → `LocalOnlyMethods`, session-control class)

| Method | Maps to |
|---|---|
| `WorkflowEnqueueItem(projectID, workflowID, workflowScope, goal string, seeds json.RawMessage)` | builds the `store.WorkItem` → `engine.Enqueue` (the engine creates the row and validates seeds) |
| `WorkflowCancelItem(itemID)` | `engine.Cancel` |
| `WorkflowResumeItem(itemID, targetPhase)` | `engine.Resume` |
| `WorkflowAnswerQuestion(itemID, answer)` | `engine.Answer` |
| `WorkflowResolveGate(itemID, decision, note)` | `engine.ResolveHumanGate` |
| `WorkflowReorderQueue(projectID, orderedIDs)` | `engine.Reorder` |
| `WorkflowSetQueue(active, maxStarts, concurrency)` | `engine.SetQueue` + settings persistence |
| `WorkflowListItems(projectID)` | store list (items only — no envelopes/traces; heavy payloads load on demand) |
| `WorkflowGetItem(itemID)` | store item + its phase rows |

Engine command errors (full concurrency on Resume/Answer/ResolveHumanGate,
invalid state, unknown item) return to the caller as errors — never swallowed
into a log. Updating the bound-method registration list in
`app_bindings_test.go` and classifying the new methods in
`internal/transport/internalmethods.go` is the documented add-a-method path
and is required, not gate-gaming. Regenerate bindings with the repo's
documented generator command (always `-ts`); binding diffs must be generator
output only.

## Scope amendment 1 (adjudicated BLOCKED, 2026-07-12)

Phase prompts are sibling-relative FILE references; def validates them
(confinement + `MaxPromptBytes`) but exports no body loader, and a snapshot
that freezes paths instead of text would let a mid-run definition edit
mutate a running item's prompts — a frozen-snapshot (D8) violation.

Authorized addition to `internal/workflow/def` (this and nothing else):

- `func InlinePrompts(resolved ResolvedWorkflow) (Workflow, error)` — returns
  a copy of the workflow in which every non-empty phase prompt AND every
  fan-out/join unit prompt is replaced by its file's contents, loaded via the
  existing `confinedPath` + `readLimitedFile(MaxPromptBytes)` rules relative
  to `filepath.Dir(resolved.Path)`. Any load failure is an error naming the
  offending element. Empty prompt fields stay empty. Document on the helper
  that `def.Workflow` has two forms — authored (prompt = path) and runtime
  (prompt = body) — and `InlinePrompts` is the single transition between
  them; nothing downstream of the DefinitionSource ever sees paths.
- Unit tests in def: happy path (phase + unit prompts inlined), missing
  file, confinement escape, size cap, empty-prompt no-op, source workflow
  not mutated.

The app's DefinitionSource resolves by id/scope, then calls `InlinePrompts`
before returning, so the engine's Snapshot freezes bodies. A workflow whose
inlined snapshot exceeds the engine's 4MiB cap parks through the existing
unstartable path — no new handling needed.

## Invariants

- Engine post-validation (`def.ValidateEnvelope`) is the sole success
  authority; never gate on provider error flags or turn status alone.
- A workflow thread's session never starts without its phase schema attached.
- Answer turns continue the prior attempt's thread; every other attempt gets
  a fresh thread.
- `Runner.Stop` on an unknown key is a silent no-op returning `(nil, nil)`.
- Workflow-mode threads never appear in normal thread lists and are not
  creatable through `CreateThread`/`UpdateThreadMode`.
- No engine FSM/teardown/drain rework — the Answer command is additive.
- Transport boundary stays clean: emissions via the app's emit path only;
  every new bound method classified in `LocalOnlyMethods`.
- Errors are user-facing state, not log entries.
