## Context you must know first

- `internal/workflow/engine/AGENTS.md` — the engine invariants. The
  command-loop goroutine owns every FSM transition; lifecycle actions
  (`item_actions.go`: `RemoveQueued`, `ParkDisposition`) are the
  precedent for state changes on items the scheduler map no longer
  tracks (direct store update + `workflow:item-state` event, serialized
  through the command loop).
- `app_workflow_disposition.go` — disposition saga: validate → external
  git action → receipt persist → optional auto-cleanup → emit. The
  mutex `workflowDispositionMu` serializes it.
- `internal/git/forge.go` — the `Forge` interface; `github.go`
  (`gh`), `gitlab.go` (`glab`), `nullForge`. `Core.CreatePR` dispatches
  per detected forge. Other `CreatePR` callers exist outside workflows —
  find them all; they must keep today's behavior (empty base = forge
  default) byte-for-byte.
- `internal/transport/internalmethods.go` — every new mutating App
  method goes into `LocalOnlyMethods`; regenerate
  `methods_gen.go` via `go run ./internal/transport/methodgen`
  (`methods_gen_test.go` gates drift).
- Wire params are positional. Changing an App method's signature changes
  the generated TS wrapper; you must mechanically update every existing
  call site (frontend `src/`, `e2e/tests/`) so the gates stay green —
  pass the neutral value, change no behavior.
- `e2e/AGENTS.md` + `e2e/tests/workflows-helpers.ts` — the e2e harness
  drives the real engine. `waitForWorkflowState(harness, id, state,
  reason)` waits on `workflow:item-state`.

### 2. Failed re-enqueue (R-A; finding B4=F2.1)

New engine lifecycle action `ReenqueueFailed(itemID string) error` in
`item_actions.go` + a new bound method `WorkflowReenqueueFailedItem`:

- Valid only from `failed`; anything else errors with the current state.
- Rebuild the runtime item from the persisted snapshot + phases the way
  `loadParked` does (target phase = latest attempt's phase, attempt
  reset). A failed item without a decodable snapshot is an error, not a
  crash.
- Prime `item.feedback` with re-enqueue guidance derived from the latest
  attempt's output envelope (its human-readable summary/diagnosis
  content — read `internal/workflow/runner`'s envelope shape and reuse
  whatever field the reject/loop feedback path uses) prefixed with the
  typed failure reason. Feedback flows through the existing
  `PhaseInput.Feedback` mechanism; do not invent a parallel channel.
- State goes `failed → queued` (direct store update + event, reason
  cleared, endedAt cleared), sort position = queue tail (dense per
  project, consistent with how enqueue assigns positions), then insert
  into the queued list and `schedule()`.
- MUST-VERIFY: per-item wall-clock budgets measure from the persisted
  item start time. Confirm how the start path sets `StartedAt` and make
  a re-enqueued item measure from its new start, not the original run.
  State what you found in the report.
- Accepted limitation (state it in a code comment where feedback is
  primed): the in-memory guidance seed does not survive an app restart
  between re-enqueue and start — same durability class as the
  transient process-N queue bound. The diagnosis itself stays in phase
  history.
- Engine tests: re-enqueue from failed drains and completes with the
  feedback visible in the next attempt's input envelope; re-enqueue on
  non-failed states errors; re-enqueued item lands at queue tail.
- e2e (one spec, in `e2e/tests/workflows-run-actions.spec.ts` or a new
  file per that suite's worker-fixture isolation rules): drive a run to
  `failed` (`check-failed-genuine` — see the sidebar suite for the
  fixture shape), call `WorkflowReenqueueFailedItem` over RPC, wait
  `failed → queued`, then let it run to done.

### 3. Disposition parks are recoverable (R-B; finding B5)

- `engine.resume` (`engine.go`): reject `ReasonDisposition` with an
  error that names the disposition actions as the path forward.
- New engine lifecycle action `ResolveDisposition(itemID string) error`
  in `item_actions.go`: valid only from `needs-human(disposition)`;
  moves the item to `done` (direct store update + event, reason
  cleared, keep the original endedAt semantics consistent with
  `parkDisposition`'s).
- `validateWorkflowDispositionState`: merge and PR accept
  `needs-human` + reason `disposition` in addition to `done`.
- `runWorkflowDisposition`: after a successful merge/PR/discard on a
  parked-disposition item, call `ResolveDisposition` so the item
  returns to `done` with its receipt. The existing
  park-on-refusal branch (done items only) stays as is; a parked item
  whose retry fails again just stays parked.
- Tests: engine tests for `ResolveDisposition` valid/invalid states and
  for `resume` rejecting disposition; app-level test that a parked
  disposition item can merge and ends `done` with a receipt.

### 4. PR base branch (finding B9)

- `Forge.CreatePR` gains a `base string` parameter (empty = forge
  default, preserving today's behavior for every existing caller —

### 5. Landed disposition must not surface as an RPC error (finding B10)

In `applyWorkflowDisposition`, an auto-cleanup failure after the
receipt was persisted currently returns as the method error — the
frontend shows a failure toast for a merge that landed. Change the
contract: the receipt gains `CleanupFailed bool
\`json:"cleanupFailed,omitempty"\``; on cleanup failure, set it,
persist the updated receipt, emit the failure through the existing
`workflow:error` event channel (with the item id), and return the
receipt with a nil error. Test: cleanup failure still returns the
receipt, marks it, and emits.

### 6. Orphan work items of deleted projects (finding B11)

work items app-wide (empty `ProjectID` filter — supported as of P3.7)
for queued/running/needs-human states, and for any item whose project
id is not in the projects list: mark it `cancelled(interrupted)`
directly in the store, emit `workflow:item-state`, and log one line per
item. Test: seed an item whose project row is absent; rebuild cancels

### 7. Discard works where it's offered (R-D; finding C6)

Discard is the destructive dismissal affordance — the armed
double-press in the UI is the authorization. In
`applyWorkflowDisposition` / `validateWorkflowDispositionWorktree`:

- Split validation: merge/PR keep the full worktree validation
  (registered, clean) exactly as today. Discard: when
  `item.WorktreePath` or `item.Branch` is empty (read-only workflows,
  setup-failed parks, pre-provision states), skip worktree removal
  entirely and write a record-only receipt. When a worktree IS present,
  keep the registration check but drop the dirty-tree refusal for
  discard; the removal call must be able to remove a dirty workflow
  worktree (inspect `RemoveOtherWorktreeForProject`'s force semantics
  and use the narrowest thing that achieves this — if that method
  cannot express it without loosening safety for other callers, that
  is a BLOCKED condition, not an invitation to fork a copy).
- Tests: discard with no worktree (record-only receipt, state per R-B
  rules when parked), discard with a dirty worktree succeeds, merge on
  a dirty worktree still refuses.
