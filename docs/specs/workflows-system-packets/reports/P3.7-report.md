## UI-vs-spec discrepancies observed

1. The sidebar initially loaded no workflow rows because
   `WorkflowListItems("")` treated the empty project ID as a literal filter.
   This was a shipped bug, reported as BLOCKED, fixed by the adjudicator, and
   codified by Scope Amendment 1. The final specs assert the intended app-wide
   footer and project-section behavior unchanged.
2. Up-next queued cancel initially called the running-only
   `WorkflowCancelItem`. This was a shipped bug, fixed by the adjudicator and
   codified by Scope Amendment 1. The final UI spec asserts the armed action
   removes the row through `WorkflowRemoveQueuedItem`.
3. Intake initially stringified compact seeds before passing the
   `json.RawMessage` argument. This was a shipped bug, fixed by the adjudicator
   and codified by Scope Amendment 2. The final spec submits the raw typed seed
   object through the UI unchanged.
4. The run-detail header renders the terminal state as lowercase `done`, while
   UI-SPEC §5.1 describes neutral `Done`. The action spec asserts lowercase
   `done` because that is the shipped DOM transition it must prove; it separately
   proves the neutral/dim sidebar presentation. This casing difference did not
   alter the required transition or actions and is recorded here for the later
   conformance/taste audit.

No required behavior was skipped or weakened.

## ASSUMPTIONS

- A paused queue is required before seeding or submitting a queued target, so
  shared helpers call `WorkflowSetQueue(false, 0, 1)` before those flows.
- Per Scope Amendment 1, a queued ordering seed is retired with
  `WorkflowRemoveQueuedItem`; `WorkflowCancelItem` remains reserved for a run
  that has reached running state.
- The intake definition's required top-level `goal` input intentionally causes
  the dialog to show both the run goal and a typed `goal` seed. The spec fills
  both visible required fields before submission.
- Notification activation events remain replayable for the lifetime of a
  harness backend, while `HarnessReset` deletes their target records. Distinct
  no-op worker fixture identities therefore give each ordinary workflow surface
  a clean worker pool and each cold deep-link case its own backend. This keeps
  the mandated one-backend-per-worker model while preventing stale activation
  replay from redirecting or satisfying another test.
- The existing chat root's `data-thread-id` is the stable identity of the pane's
  open thread; the triage deep-link spec uses it only to verify persisted mode
  and project ownership through the bound `GetThread` method.
- The mock provider writes no files, so the review companion assertion covers
  its chrome and empty state rather than diff rows, as directed by the packet.
