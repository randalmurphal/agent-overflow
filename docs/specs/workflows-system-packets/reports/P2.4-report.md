## ASSUMPTIONS

- The user-provided lane baseline was accepted as green; the packet gates were still rerun against the completed tree.
- The store/config directory passed through `initSubsystems` is the existing app-managed data root, so narratives live below `<dbDir>/workflow-runs/...` and no second root is introduced.
- An authored phase with an empty shape means the existing default single shape; any explicit non-single shape is rejected by the runner.
- Workflow phases use the persisted project's root path as `WorkspacePath`; worktree-per-run remains deferred to P2.6.
- `WorkflowEnqueueItem` preserves `goal` as the work-item goal and preserves the caller's `seeds` JSON as workflow inputs; it does not silently synthesize or merge a `goal` seed.
- The persisted `WorkflowScope` is authoritative even if a workflow with the same id exists in the other scope.
- Queue active/concurrency are persisted. `maxStarts` is deliberately process-bound and is not persisted, matching the engine config contract.
- A completed/stopped attempt releases runner schema ownership. A question answer re-registers the same phase schema before any send or lazy session respawn, so a workflow session can never start schema-less while parked threads do not leak registry entries.
- Workflow events use the canonical `emitWithReplay` path. The transport event bus provides bounded per-channel reconnect replay. The optional persistent diagnostic replay remains per-thread and therefore does not record item/queue workflow payloads, which intentionally carry no `threadId` in the existing engine event contract.
- `Runner.Stop` must return `(nil, nil)` even if provider interruption fails. Such a failure is handled visibly in application logs after runner-local state is released; v1 has no partial-envelope recovery channel.
- No setup hooks, workflow env/secrets, budgets, watchdog/backoff, fan-out/join execution, tool drivers, worktrees, derived read-only behavior, or frontend workflow subscription was inferred into this packet.

## Runner state machine

1. **Validate** — accept only `driver=agent` and empty/`single` shape; build the full phase envelope schema.
2. **Prepare** — create the attempt narrative directory, create a fresh workflow thread unless `PriorThreadID` is present, and attach thread/narrative to the persisted phase row.
3. **Arm** — build the interpolated prompt, subscribe the turn observer, register the thread schema, and publish the active run.
4. **Send** — serialize the send against Stop and recheck active ownership immediately before sending.
5. **Observe** — terminal session/turn failure becomes `execution-failure`; other events are ignored until `turn_complete`.
6. **Validate envelope** — a present payload passing `def.ValidateEnvelope` becomes `done`, `question`, or `stuck`.
7. **Feedback retry** — the first absent/invalid payload sends one findings message on the same thread with the same schema. A second absent/invalid payload becomes `execution-failure`.
8. **Finish** — remove run/schema ownership, unsubscribe, wait out any serialized send, and deliver the outcome once.
9. **Stop** — unknown runs are a no-op; known runs remove local ownership first, prevent queued retry sends, interrupt the provider turn, and return `(nil, nil)` with no partial envelope.

## Exact system-owned prompt suffix

`${ABSOLUTE_NARRATIVE_PATH}` is replaced with the system-created absolute path.
The `<workflow-feedback>` block is omitted entirely when feedback is absent;
when present, `${NOTE}` is the note (or `(none)`) and `${VALUES_JSON}` is
indented JSON (an empty object when values are nil).

````text
<workflow-system-instructions>
Write a concise narrative of the work performed, decisions made, and validation results to this file:
${ABSOLUTE_NARRATIVE_PATH}
The narrative is for human inspection and is not part of the control envelope.
<workflow-feedback>
Note:
${NOTE}
Values:
```json
${VALUES_JSON}
```
</workflow-feedback>
Your final message must satisfy the attached schema; status must be done, question, or stuck.
</workflow-system-instructions>
````

## Thread and provider-session lifetime

- Normal initial/resume/gate-loop phase attempts create one new
  `mode=workflow` AO thread per attempt. Only question answers set
  `PriorThreadID`, producing the next attempt on the parked attempt's same AO
  thread.
- Claude receives the schema in `claude.Config.OutputSchema` at every session
  spawn. Initial, retry, and answer turns use the same live Claude session when
  it exists. If the session was reaped or the app restarted, the answer start
  registers the schema first and the normal stored `SessionRef` resume path
  recreates that thread's provider context with the same sticky schema.
- Codex workflow sessions cannot spawn without a registered schema, and every
  initial, retry, and answer send includes the schema again in
  `SendOptions.OutputSchema`. Live continuations use the same Codex session;
  lazy respawn/resume uses the AO thread's stored provider thread reference and
  still sends the schema per turn.
- Generic abnormal-death auto-reconnect is disabled for workflow threads. A
  failure parks through the runner/engine, and only an explicit engine-owned
  continuation may recreate the provider session.
