## Assumptions

1. The `go.mod`/`go.sum` delta is the packet-permitted output of `go mod
   tidy`, not an independently selected dependency. The pinned Wails fork
   already requires `git.sr.ht/~jackmordaunt/go-toast/v2 v2.0.3`; importing
   its notifications package makes Go's lazy module loader retain that
   existing transitive module explicitly.
2. The binding decision for a headless backend with a live transport but no
   subscribed launcher takes precedence over the broader degraded-path prose:
   an accepted ring publish returns nil and logs the absent dedicated
   subscriber once. A missing transport and harness mode return typed
   `unavailable` errors.
3. Windows' `-Embedding` toast activation should run the normal launcher boot.
   That lets Wails register its COM callback immediately while the same bounded
   cold-click queue waits for WSL/bootstrap/bridge readiness.
4. `sessionStorage` is the appropriate page-reload activation checkpoint. The
   checkpoint is scoped to the per-boot bootstrap token so it cannot suppress
   an early activation after a backend restart; the token is already held in
   the same storage by the existing transport bootstrap flow.
5. A launcher activation RPC is not retried after a write is attempted because
   a disconnect makes backend receipt ambiguous. This preserves the packet's
   one-click/one-backend-event contract without inventing an idempotency store.
6. Only `notifications.DefaultActionIdentifier` is activation. Every other
   identifier, including macOS dismiss and the fixed Linux reason-2 close path,
   is ignored.
7. Dynamic imports in `eventsNotification.ts` intentionally isolate the small
   routing store from unrelated narrow Vitest module mocks. Vite reports that
   these modules are also statically reachable and therefore are not separate
   chunks; no code-splitting benefit is claimed.

## Launcher client placement

The minimal WS bridge client lives in
`internal/wsllauncher/notification_client.go`, alongside bootstrap and WSL
lifecycle code. Its protocol, reconnection, ordering, and RPC behavior are
platform-neutral and therefore execute in the normal Linux Go test suite. The
Windows-only Wails service and presentation callback remain in
`cmd/agent-overflow-windows/notifications.go`. The cold-click queue is also in
`internal/wsllauncher` solely to make its bounded FIFO/drain state executable
off-Windows; launcher lifecycle and goroutines remain owned by the command.

## Activation flow maps

### In-process Linux/macOS desktop

1. Wails response callback filters to the default action and decodes the target:
   `app_notifications_desktop.go:158-171`.
2. Backend validation emits the sole frontend channel:
   `app_notifications.go:171-175`.
3. Frontend subscription enters the notification handler:
   `frontend/src/lib/stores/events.ts:159-161` →
   `frontend/src/lib/stores/eventsNotification.ts:108-109`.
4. The bounded queue validates/waits for hydration and opens a known thread:
   `frontend/src/lib/stores/eventsNotification.ts:30-41,50-89,102-104` →
   `frontend/src/lib/stores/panes.svelte.ts:419`.

### Windows/WSL launcher bridge

1. Headless `notifyOS` publishes the typed send payload into the event ring:
   `app_notifications.go:196-215`.
2. The narrow launcher client buffers replay/live races, validates, and invokes
   native presentation: `internal/wsllauncher/notification_client.go:213-249,350` →
   `cmd/agent-overflow-windows/notifications.go:98-109`.
3. A default-action toast response validates and queues its target:
   `cmd/agent-overflow-windows/notifications.go:117-140` →
   `cmd/agent-overflow-windows/main.go:997-1005`.
4. The serialized drain posts the local-only RPC:
   `cmd/agent-overflow-windows/main.go:1009-1026` →
   `internal/wsllauncher/notification_client.go:271-308`.
5. The backend method converges on the same event emission and frontend path:
   `app_notifications.go:179-183` → `app_notifications.go:171-175` → the
   in-process frontend steps 3-4 above.

## Verification honesty

Real Windows/WSL toast presentation and click-through, real macOS notification
presentation/click/dismiss, and real Linux desktop notification
presentation/click/dismiss were not executable in this Linux CI-like
environment. They require user-assisted verification on each OS surface.

The Windows gate compiles the launcher and bridge but runs no Windows-tagged
tests. A separate `GOOS=windows go test -c ./cmd/agent-overflow-windows` focused
check confirmed those tests compile; the cross-platform bridge and queue tests
execute on Linux. Playwright exercises the honest harness claim only: a typed
unavailable send error plus synthetic activation through backend emission,
transport replay/pre-hydration queue, and pane focus. It does not claim native
OS presentation.

## Claude review riders (post-codex)

Applied during review, before merge; all seven gates re-run green over the
final tree (vitest 363 files / 5243 tests, e2e 11/11).

1. **`internal/notify` shared wire package.** The packet output duplicated
   the notification wire contract (target/send structs, validation, content
   limits, channel names) between package `main` and `internal/wsllauncher`,
   because the launcher cannot import the root package. The contract now
   lives once in `internal/notify` (`Target`, `Send`, `ValidateTarget`,
   `TargetToMap`/`TargetFromMap`, limits, channel constants, `NewID`).
   Drift between two validators across a process boundary would have made
   the launcher silently discard notifications the backend considers valid.
   Bindings regenerated; the `NotificationTarget` TS model moved to the
   `internal/notify` namespace.
2. **`notificationActivationQueue.ts` factory split.** The activation-queue
   factory moved out of `eventsNotification.ts` into its own module with no
   store imports; the singleton wiring now uses static imports with
   call-time closures instead of dynamic imports (report assumption 7).
   Vitest mock proxies throw when module-eval code touches an export a
   partial `vi.mock` factory omitted — TerminalView.test.ts surfaced
   exactly that during the review gate run — and the closures defer the
   access to activation time. The split also removes both
   INEFFECTIVE_DYNAMIC_IMPORT build warnings.
3. **`e2e/AGENTS.md`** now documents `notifications.spec.ts`.
