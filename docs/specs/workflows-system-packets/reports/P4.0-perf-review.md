# P4.0 perf/memory review — workflows hot paths

Read-only codex consult (gpt-5.6-sol, xhigh, session
`019f5985-8b4f-7022-941f-f9a9660940ec`) over the post-P3.9 tree
(content-identical to merged 9314ba8f for all workflow code).

The workflows system is sound at small scale, but its authoritative-refresh design multiplies work sharply with project count and retained history. The main issue is not raw engine event volume; it is the broad RPC, filesystem, SQLite, and frontend work triggered by each compact event.

This was a static review. The supplied `~620s` race-suite duration is treated as measured input. Independent timing was blocked because the read-only environment could not create Go’s temporary build directory. No files were modified; the worktree remains clean.

## Ranked findings

### 1. High — Item-state refreshes fan out into all-project catalog and history reloads

Files: [workflowsSidebar.svelte.ts:98](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsSidebar.svelte.ts:98), [workflowsSidebar.svelte.ts:146](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsSidebar.svelte.ts:146), [workflowData.ts:41](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowData.ts:41), [workflowsPane.svelte.ts:271](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:271), [workflowsPane.svelte.ts:310](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:310), [workflowsPane.svelte.ts:438](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:438), [app_workflow_data.go:82](/home/rmurphy/repos/ao-lanes/p39/app_workflow_data.go:82)

Structural facts:

- Every `workflow:item-state` immediately patches local state, then schedules a full sidebar refresh.
- The sidebar refresh performs one app-wide `WorkflowListItems('')`, then `WorkflowListDefinitions` for every known/project-bearing ID.
- When the pane is active, the same event reloads items, item costs, and definitions for every selected project.
- One `WorkflowListDefinitions` performs three SQLite queries—`GetProject`, `MAX(sort_position)`, and queued-position `COUNT`—plus profile YAML loading, workflow discovery/parsing, prompt validation, and catalog construction.
- Sidebar and pane do not share the definition results.

Let `P` be sidebar projects and `K` pane-selected projects. One authoritative refresh wave produces:

- RPCs: `1 + P + 3K`
- SQLite queries: `1 + 3P + 5K`
- Definition/profile filesystem work: `P + K` full catalog loads

With all 20 projects selected, that is 81 RPCs and 161 SQLite queries per wave, before current-run detail or diff refreshes.

Coalescing prevents concurrent refresh growth, but does not bound total work across a sustained drain:

- One event starts a refresh.
- Any number of events during that refresh set one trailing-refresh flag.
- If all events finish before the first request returns, the burst costs at most two waves.
- Events arriving during the trailing wave schedule another wave. Sustained events therefore keep the reload loop continuously active at roughly one wave per reload latency.

This is acceptable for a small number of projects and occasional transitions. It is not acceptable for many projects or a rapid mocked/automated drain, especially because definitions cannot have changed as a consequence of an item-state transition.

Concrete fix:

- Include `projectId` and authoritative summary fields—timestamps, disposition, branch/worktree metadata if actually needed—in `workflow:item-state`, or add a lightweight `WorkflowGetItemSummary(itemID)` fallback.
- Refresh only the affected project, not every project.
- Separate catalog refresh from item refresh. Cache definitions until a workflow/profile/config revision event, explicit editor action, or intake open.
- Let the pane refresh the current detail only when the event concerns that item.
- A short trailing debounce can reduce bursts, but should be secondary to narrowing the data dependency.

Expected effort: large; this touches event DTOs, frontend stores, catalog invalidation, and tests.

### 2. High — `WorkflowListItemCosts` has no usable `project_id` index

Files: [usage_ledger.go:134](/home/rmurphy/repos/ao-lanes/p39/internal/store/usage_ledger.go:134), [migrate.go:908](/home/rmurphy/repos/ao-lanes/p39/internal/store/migrate.go:908), [migrate.go:1069](/home/rmurphy/repos/ao-lanes/p39/internal/store/migrate.go:1069), [app_workflow_data.go:152](/home/rmurphy/repos/ao-lanes/p39/app_workflow_data.go:152)

Structural facts:

```sql
SELECT work_item_id, SUM(cost_usd)
FROM usage_ledger
WHERE project_id = ? AND work_item_id != ''
GROUP BY work_item_id
```

The actual indexes are on:

- `created_at`
- `(thread_id, created_at)`
- `(work_item_id, created_at)`

None starts with `project_id`. SQLite therefore has to inspect the lifetime ledger—or an equally broad existing index—to answer each project query. The active pane issues this once per selected project per refresh wave, making the cost approximately `O(K × U)`, where `U` is lifetime usage-ledger size.

This hurts pane opening and busy drains on long-lived installs. It does not affect an idle app with the workflows pane closed.

Concrete fix:

- Add a migration for a partial index such as:

```sql
CREATE INDEX idx_usage_ledger_project_work_item
ON usage_ledger(project_id, work_item_id)
WHERE work_item_id <> '';
```

- Add an `EXPLAIN QUERY PLAN` assertion using the established store-test helper.
- Longer term, a single multi-project grouped query would avoid `K` RPCs, but the index is independently necessary.

Expected effort: small.

### 3. High — Work-item history is unbounded and hydrated far beyond what each view needs

Files: [work_items.go:131](/home/rmurphy/repos/ao-lanes/p39/internal/store/work_items.go:131), [app_workflow.go:406](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:406), [workflowData.ts:41](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowData.ts:41), [workflowData.ts:80](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowData.ts:80), [workflowsPane.svelte.ts:54](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:54), [WorkflowDetail.svelte:27](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/components/workflows/WorkflowDetail.svelte:27), [WorkflowDetail.svelte:134](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/components/workflows/WorkflowDetail.svelte:134)

Structural facts:

- Workflow records deliberately have no project FK and no retention/delete path. Records therefore accumulate indefinitely.
- S11 is confirmed: the sidebar calls `WorkflowListItems('')`, transferring every retained item before filtering terminal rows in JavaScript.
- No existing index has `(sort_position, created_at)` as leading columns, so the app-wide unfiltered ordering cannot be satisfied directly by the current indexes.
- The active pane loads all items for every selected project.
- The workflow-detail page renders every terminal history row without paging or virtualization.
- Every item-state patch maps over the whole pane array, allocating a new `W`-element reference array.
- The pane retains all loaded items, costs, and definitions while active.

The sidebar itself only needs:

- Per-project attention/live counts.
- Compact rows for queued, running, unresolved human attention, unresolved failures, and undisposed completion.
- IDs, goal, workflow identity, state/reason, queue order, and relevant timestamps.

A simple state filter is only a partial fix. Current logic keeps every failed item forever, even after it has a disposition receipt, because `isWorkflowSidebarRun` excludes resolved `done` rows but not resolved `failed` rows. That lifecycle policy needs to be made explicit server-side.

The pane has two distinct requirements:

- Overview: active/attention counts and queued rows.
- Workflow detail: live rows plus pageable history.

Concrete fix:

- Add a dedicated sidebar summary/list endpoint with a server-side unresolved/live predicate and compact DTO.
- Add an overview endpoint returning per-workflow counts and queued rows, not full history.
- Page workflow history by `(ended_at, id)` or an equivalent stable cursor.
- Query costs only for displayed rows or return them in the grouped overview/history response.
- Decide whether a failed item with a disposition is resolved; encode that consistently in the backend predicate and frontend sweep logic.

Expected effort: large, but it is the durable fix for S11 and frontend memory scaling.

### 4. Medium-high — `WorkflowGetItem` returns much more than the live UI consumes

Files: [app_workflow.go:413](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:413), [app_workflow.go:420](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:420), [work_items.go:11](/home/rmurphy/repos/ao-lanes/p39/internal/store/work_items.go:11), [work_item_phases.go:10](/home/rmurphy/repos/ao-lanes/p39/internal/store/work_item_phases.go:10), [WorkflowRunDetail.svelte:59](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/components/workflows/WorkflowRunDetail.svelte:59), [workflowsPane.svelte.ts:339](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:339), [workflowsPane.svelte.ts:396](/home/rmurphy/repos/ao-lanes/p39/frontend/src/lib/stores/workflowsPane.svelte.ts:396)

B2 is confirmed, but the phase payload is at least as important as the snapshot.

`WorkflowGetItem` returns:

- The complete item, including the frozen definition snapshot, seeds, budget, digest, and other fields.
- Every phase attempt with input envelope, output envelope, gate trace, intervention, and narrative path.
- Artifact metadata, requiring filesystem directory reads and per-entry stats.
- Usage aggregation.

The frontend consumes:

- Snapshot: only the IDs of tool/check phases.
- Phases: ID, attempt, thread ID, status, start/end timestamps, and the latest question-bearing output.
- Artifacts and usage.
- It does not consume phase input envelopes, gate traces, interventions, or narrative paths.

The snapshot limit is 4 MiB. Stock starter sources total only about 4.4–9.4 KiB before JSON encoding, so snapshot size is not an urgent problem for built-ins. Custom prompt-heavy workflows can approach the cap, and the frontend reparses the snapshot to derive check IDs whenever that detail rerenders.

Phase history can grow more sharply: each input envelope contains the reconstructed variable context, so later attempts repeat prior outputs. Returning all of those inputs on every current-run refresh can become quadratic in transferred bytes.

Current-run phase events trigger `WorkflowGetItem`; item-state events can also run an overview refresh followed by another detail refresh. Coalescing serializes these calls but still repeatedly ships the full detail.

Concrete fix:

- Introduce a deliberate `WorkflowItemDetailView` DTO.
- Return `checkPhaseIds` explicitly instead of exposing the full definition snapshot.
- Return slim phase timeline rows and a separate `question` field derived from the latest relevant output.
- Keep raw input/gate/intervention data behind an explicit diagnostics endpoint if it is needed later.
- Avoid artifact filesystem scans while the item is non-terminal, or load artifacts separately when the outputs section becomes relevant.

Trimming only `snapshot` while leaving full phase internals would not be worth a bespoke compatibility mechanism. Replacing the implicit snapshot dependency with a coherent view DTO is worth the coupling and actually reduces frontend/backend coupling.

Expected effort: medium.

### 5. Medium — Resource-wait scheduling scans every queued item on every scheduler wakeup

Files: [semaphores.go:71](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/semaphores.go:71), [drain.go:14](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/drain.go:14), [engine.go:545](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/engine.go:545), [drain.go:74](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/drain.go:74)

Structural facts:

- `e.items` contains all queued and running runtime items.
- Every `schedule()` begins with `startWaiting()`.
- `startWaiting()` scans the entire map to find the small subset marked `waiting`, then sorts that subset.
- `schedule()` runs after enqueue, completion, runner startup settlement, cancellation, gate decisions, and queue changes.

With `Q` queued items and at most 32 running slots, this makes scheduler wakeups `O(Q)` even when zero or one items are waiting for a project resource. Because it runs inside the single owner goroutine, the scan delays every FSM command.

Queue slice maintenance adds secondary `O(Q)` work when compacting a consumed head before insertion/removal. Normal tail enqueue is usually cheap, so this is less important than the map scan.

This hurts a paused or busy queue with thousands of queued items. Finished items do not contribute because terminal items are evicted.

Concrete fix:

- Maintain a dedicated ordered waiting collection and membership map.
- Insert/remove items when their `waiting` flag changes rather than rediscovering them by scanning `e.items`.
- If contention becomes common, keep project/resource keyed waiter sets so a release only revisits potentially eligible items.
- Preserve queue ordering as the waiter priority key.

Expected effort: medium.

### 6. Medium — App event hooks synchronously reload full item rows on the engine goroutine

Files: [app_workflow.go:29](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:29), [app_workflow_digest.go:46](/home/rmurphy/repos/ao-lanes/p39/app_workflow_digest.go:46), [app_workflow_notifications.go:37](/home/rmurphy/repos/ao-lanes/p39/app_workflow_notifications.go:37), [fsm.go:44](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/fsm.go:44)

`Emitter.Emit` is documented to return promptly, but the app wrapper performs synchronous database work before and after transport emission.

For a normal successful item:

- `queued → running`: `afterWorkflowStateEvent` loads the full item.
- `running → done`: it loads the full item before merely queueing disposition work.
- `needs-human` or `failed`: the pre-hook loads the full item and latest phase, writes a digest, then the post-hook loads the full item again.

`GetWorkItem` includes the frozen snapshot, so a large snapshot is copied from SQLite on the engine’s single command goroutine. This is two full item reads per normal run and more for attention outcomes.

Concrete fix:

- Add `projectId` to `StateEvent`; this also enables finding 1’s affected-project refresh.
- Skip item reads for transitions where the hook only needs item ID or project ID.
- Use a slim notification/digest query for attention transitions.
- Preserve the digest-before-visible-event ordering, but move non-order-critical OS notification and tally work off the owner goroutine after capturing the small required values.

Expected effort: medium.

### 7. Medium — Phase-context reconstruction becomes quadratic in attempt count

Files: [context.go:18](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/context.go:18), [drain.go:203](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/drain.go:203), [fsm.go:174](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/fsm.go:174), [work_item_phases.go:90](/home/rmurphy/repos/ao-lanes/p39/internal/store/work_item_phases.go:90)

Each phase attempt:

- Calls `variableContext` before starting.
- Calls it again on successful completion.
- Each call loads every historical phase row, including all envelopes and traces.
- It scans all rows to choose latest completed outputs and decodes every selected output.
- `loopCounts` and `nextAttempt` scan the same history again.

Across `A` attempts this is approximately `O(A²)` row materialization and JSON decoding. Loop maxima have a lower-bound validation but no global upper bound, so a valid authored workflow can accumulate many attempts.

This is not an item-count problem and will not matter for ordinary 2–8 phase runs. It becomes material for long loop/retry histories, especially with large output envelopes and repeated cumulative input contexts.

Concrete fix:

- Rebuild an active item’s latest-output, loop-count, and attempt-count state once from SQLite, then update it incrementally as attempts complete.
- Keep SQLite authoritative; the cache only belongs to the active runtime item and is rebuilt on restart.
- Alternatively, add narrow store reads that omit input envelopes and unrelated phase data, but keep route/business decisions in Go.

Expected effort: medium to large.

### 8. Low-medium — Startup rebuild reads active items twice and overhydrates parked rows

- It then lists the entire global active set again to find orphaned project IDs.
- Both paths use full `WorkItem` columns, including snapshot, seeds, and budget.

- Use summary columns for the initial classification.
- Fetch full rows only for queued/running recovery or when a pending human decision is actually resumed.

### 9. Low-medium — Live profile and definition data is repeatedly reparsed at phase boundaries

Files: [app_workflow.go:44](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:44), [app_workflow.go:94](/home/rmurphy/repos/ao-lanes/p39/app_workflow.go:94), [budget.go:63](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/budget.go:63), [semaphores.go:24](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/semaphores.go:24), [app_workflow_reliability.go:31](/home/rmurphy/repos/ao-lanes/p39/app_workflow_reliability.go:31), [app_workflow_workspace.go:59](/home/rmurphy/repos/ao-lanes/p39/app_workflow_workspace.go:59)

Each profile lookup performs a project query, file read, YAML decode, and validation. Without an item budget override, a phase normally loads the profile for both budget and runner reliability. Resource-bearing phases add another load, and initial writing-workspace provisioning adds another.

Definition validation at intake and resolution at actual start also reparses the selected scope. Re-resolving at start is semantically justified for queued items because the frozen snapshot should reflect the definition when execution actually begins.

This is smaller than the frontend-driven catalog reparsing in finding 1 and is unlikely to matter with stock, small profiles.

- Consolidate profile reads within one phase boundary where live semantics permit.
- Preserve live resource-capacity behavior through invalidation; do not cache indefinitely.
- Keep the enqueue/start definition revalidation distinction unless the queue contract is deliberately changed.

## Event-volume and transport assessment

Files: [fsm.go:76](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/fsm.go:76), [drain.go:231](/home/rmurphy/repos/ao-lanes/p39/internal/workflow/engine/drain.go:231), [eventbus.go:109](/home/rmurphy/repos/ao-lanes/p39/internal/transport/eventbus.go:109), [eventbus.go:153](/home/rmurphy/repos/ao-lanes/p39/internal/transport/eventbus.go:153), [conn.go:303](/home/rmurphy/repos/ao-lanes/p39/internal/transport/conn.go:303)

For a successful workflow with `F` phases and no loops:

- `F` phase-running events.
- `F` phase-completed events.
- One `queued → running` item event.
- One `running → done` item event.

Baseline: `2F + 2` workflow events per item.

Automatic disposition and asynchronous digest upgrades can add compact same-state item refresh events. Queue events are not emitted for every ordinary transition.

The transport implementation is already appropriate:

- Per-channel rings are fixed at 1,000 events.
- Workflow payloads are compact and do not contain snapshots.
- Payload JSON and the live wire frame are encoded once per emit, not once per subscriber.
- A batched connection frame does re-encode the small raw messages, but this is minor at workflow event rates.

The raw workflow event stream is not a performance concern. The expensive part is the frontend reload work caused by item-state events.

## Test infrastructure — shared migrated template database

Files: [store_test.go:15](/home/rmurphy/repos/ao-lanes/p39/internal/store/store_test.go:15), [store.go:17](/home/rmurphy/repos/ao-lanes/p39/internal/store/store.go:17), [migrate.go:1215](/home/rmurphy/repos/ao-lanes/p39/internal/store/migrate.go:1215), [migrate_test.go:36](/home/rmurphy/repos/ao-lanes/p39/internal/store/migrate_test.go:36)

Distinct test-infrastructure finding:

- Measured input: `internal/store` takes about 620 seconds under `-race`.
- Structural count: 430 `newTestStore(t)` calls across 460 tests.
- Every helper call creates a new `:memory:` database and runs all 26 migrations.
- The chain currently contains eight rebuild migrations and five Go fixups.
- This means the helper executes approximately 11,180 migration applications and 3,440 rebuild migrations per suite run.
- No store tests currently use `t.Parallel`, though the solution should remain parallel-safe.

A migrated template database is feasible and likely high leverage.

Suggested design:

1. In package `TestMain`, create one file-backed template DB.
2. Run `New(templatePath)` once.
3. Seed the default project once with deterministic timestamps.
4. checkpoint/truncate WAL and close the template.
5. For each `newTestStore`, byte-copy the closed main DB into `t.TempDir()`.
6. Open the clone through `New(clonePath)`. It will still apply PRAGMAs and verify the migration version, but skip all applied migrations.
7. Close the clone in `t.Cleanup`.

Keep true migration tests on blank databases:

- `runMigrations` idempotency and step-through tests already construct their own DBs.
- `TestMigrationFreshDB` should explicitly use a blank `New(path)` so at least one test continues proving the complete fresh chain.
- Tests that depend on `:memory:` journal behavior should remain explicit exceptions.

The template is read-only after construction, so concurrent copying is safe if tests later become parallel. Explicitly closing and checkpointing it avoids copying a live `-wal`/`-shm` pair.

Expected savings:

- Migration execution count drops by about 99.8%: 430 full chains become one full chain plus 430 cheap copies/opens.
- Wall-clock savings are not independently measured. If migration setup is the dominant race cost, cutting hundreds of seconds is plausible; file-copy overhead means the result will not be the full theoretical reduction.
- Benchmark the helper setup before/after under `-race` and keep the change only if it materially beats `:memory:` construction.

Expected effort: medium, mostly test-helper and migration-coverage adjustments.
