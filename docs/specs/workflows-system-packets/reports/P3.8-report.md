## Implementation notes

- Failed re-enqueue rebuilds from the frozen snapshot, targets the latest
  persisted attempt's phase, resets the runtime attempt, moves the item to the
  project queue tail, and primes the existing `Feedback` channel with the typed
  failure reason plus `diagnosis`/`summary` envelope outputs.
- Wall-clock budget verification: `budget.go` measures elapsed time from the
  persisted `WorkItem.StartedAt`. Both an ordinary start and the new re-enqueued
  start call `UpdateWorkItemRunStart` with a fresh engine timestamp before
  entering the phase and enforcing the budget. A re-enqueued run therefore
  measures from its new start, not its original run.
- The re-enqueue guidance seed is intentionally process-local. A restart while
  the item remains queued loses the seed, like the transient process-N queue
  bound; the diagnosis remains in durable phase history.
- Notification activation now runs `Show`, `Restore`, then `Focus` before
  navigation. Desktop uses the live main-window getter shared with the
  second-instance path. The Windows launcher uses its mutex-protected `win()`
  getter before queueing the backend activation.

  proxy caveat required only one physical-file edit.

  phase row; and disposition parks resolve only after receipt persistence

## ASSUMPTIONS

1. `ListWorkItemPhases` is authoritative chronological history; its final row
   is the packet's “latest attempt.”
2. Human-readable re-enqueue guidance is sourced from envelope output keys
   `diagnosis` and `summary`, using the existing `Feedback.Values` shape with
   phase-qualified names; the typed failure reason prefixes `Feedback.Note`.
   If those outputs are absent, the envelope reason is the fallback; if that is
   absent too, the typed failure reason alone remains explicit guidance.
3. Resolving a disposition park preserves the park's persisted `EndedAt`, so
   retrying disposition does not rewrite when workflow execution ended.
4. A discard item with either no worktree path or no branch is a record-only
   discard, as R-D directs; no project/worktree lookup is needed in that path.
5. `RemoveOtherWorktreeForProject(..., force=true)` is the narrow existing API
   that authorizes deletion of a dirty registered workflow worktree without
   weakening safety for its other callers.
6. After a landed disposition, failure to persist the cleanup-failure flag is
   still reported through the required `workflow:error` channel and local log,
   while the already-landed action remains a nil RPC error.
7. The intake override is trimmed but otherwise preserved after the git
   package's branch-name validation; an empty override copies the live project
   profile value. Provisioning falls back to the repository's current branch
   only when both remain empty, preserving prior behavior.
8. The packet's “bring forward” instruction means using the exact
   `Show`/`Restore`/`Focus` sequence from each second-instance exemplar.
9. Build products created by gate commands (`bin/`, `frontend/dist/`, and test
   artifacts) are gate outputs rather than source edits and are not expanded in
   the source-file inventory above.
