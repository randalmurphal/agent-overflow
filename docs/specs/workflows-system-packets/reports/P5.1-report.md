## ASSUMPTIONS

1. “Separate queues” means separate engine-owned project gates and separately rendered project groups while retaining one deterministic scheduler scan. Inter-project arbitration therefore remains the existing sorted order; skipped items stay in place and order inside every project is unchanged.
2. Per house decision 2, project concurrency 0 is uncapped except by the global pool. The UI renders a capped project as running/effective-cap and an uncapped project as the running count alone.
3. The effective displayed cap is min(nonzero project cap, global concurrency). A zero global concurrency fallback is normalized by the existing global settings rules rather than treated as an extra project semantic.
4. Project pause gates automatic queued starts. Like the existing global pause, it does not prevent an explicit user answer/gate continuation; explicit continuations still obey global and project slot caps.
5. Boot seeding through Engine.Config.ProjectQueues is the least stateful shape: config is copied into command-loop-owned maps before commands are accepted, and all live mutations still pass through a queue command.
6. Persist-first means a successful store update remains authoritative if the engine is concurrently shutting down. A later boot re-seeds the stored value; the live detached push logs a visible error.
7. A project drain summary considers queued work pending only while both global and project queues are active. Running work always prevents a flush. A tally survives a temporary project pause/resume so it cannot be lost before a real drain.
8. workflow:definitions-changed needs no payload because both pane and intake already know their active project and can reuse their full existing load paths. Coalescing all filesystem changes into one revision is intentional.
9. Watching the workflow root, shared directory, projects directory, each project directory, and recursive workflows subdirectories covers atomic writes plus create/rename of project trees. A malformed configured project path is a setup error and uses the house-approved visible log-only failure while allowing app boot.
10. The project update RPC is privileged because it persists local settings and changes process scheduling; LocalOnlyMethods is therefore required.
11. The packet’s explicit fsnotify allowance permits importing the already-selected v1.9.0 module and making that existing version direct in go.mod; changing its version or adding another package would have required BLOCKED.
