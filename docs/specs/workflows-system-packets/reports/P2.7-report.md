## ASSUMPTIONS

- The user's statement that the lane baseline was already green satisfies the
  packet's pre-edit baseline requirement; I did not rerun a redundant pre-edit
  baseline.
- Because `workflows:` is nested under one `HarnessSeedProject` and item specs
  have no scope field, seeded definitions are project-scoped and items persist
  `workflow_scope=project`.
- A definition's `name` is its plain filename stem. The YAML `id` remains the
  authoritative workflow id and may differ from the filename.
- Prompt keys are sibling-relative paths under the production project workflow
  directory. Duplicate destinations and existing files fail loudly rather than
  overwrite another fixture.
- An omitted item `target` means `queued`; an omitted/zero `count` means one.
  The supported resting targets are `queued`, `needs-human`, and `done` because
  those are deterministic production outcomes without inventing a side door.
- One seed spec may expand to at most 100 workflow items. This bounds allocation,
  database amplification, and provider subprocess work before any project/file
  mutation occurs.
- Non-queued targets are created and driven before queued targets globally so
  `maxStarts=1` always belongs to the intended item. Returned ids are rebuilt in
  the authored project/item order.
- Driving a non-queued seed while pre-existing queued workflow items exist is
  rejected visibly; otherwise the global production scheduler could consume the
  one-start budget with unrelated state.
- A `queued` target requires the caller's effective queue to be inactive. An
  active queue would immediately drain it when the caller's state was restored.
- Queue restoration includes effective active state, concurrency, and any
  positive transient `maxStarts` remainder exposed by `workflow:queue-state`.
  An already-exhausted transient budget is rejected because the existing public
  production API cannot reconstruct “persisted active, effectively paused at
  zero starts” without an out-of-scope engine change.
- Reset cancels already-running workflow items, starts each remaining queued
  item through the production scheduler, and cancels it once running. Parked and
  terminal items are already evicted from engine memory and disappear through
  the production project cascade.
- Reset removes the isolated harness config root's `projects/`, shared
  `workflows/`, and `workflow-runs/` directories. The harness data root is
  disposable and boot-time guarded, so these are harness-owned state.
- Existing direct store writes remain limited to completed ordinary-thread
  history. Workflow item and phase rows are created only by
  `WorkflowEnqueueItem` and the workflow engine.
- Mock timing/cost fields are deterministic zero values. The provider-semantic
  terminal discriminators and ordering are the contract the app parsers use.
- `afterTurns:"silent"` represents a hung in-flight turn, so it retains engine
  ownership until an interrupt instead of returning as an empty completed
  scenario.
- No Harness RPC was added: the existing `HarnessSeed` and `HarnessReset`
  methods gained data/behavior, so dispatcher or Wails binding regeneration was
  unnecessary. No generated binding was edited.

## Final `workflows:` seed schema

```text
HarnessSeedSpec
└─ projects[]
   └─ workflows (optional)
      ├─ definitions[]
      │  ├─ name: string                 # plain filename stem
      │  ├─ yaml: string                 # strict workflow YAML
      │  └─ prompts: map<string,string>  # confined sibling paths → bodies
      ├─ profile: string                 # optional project profile YAML
      └─ items[]
         ├─ workflow: string
         ├─ goal: string
         ├─ seeds: JSON object
         ├─ stepMode: boolean
         ├─ count: integer               # default 1; aggregate maximum 100
         └─ target: queued|needs-human|done  # default queued
```

Example:

```json
{
  "projects": [{
    "name": "workflow-fixture",
    "repo": {},
    "workflows": {
      "definitions": [{
        "name": "review-flow",
        "yaml": "id: review-flow\nname: Review flow\nphases:\n  ...\n",
        "prompts": {
          "review-flow.md": "Review the requested change and return the control envelope."
        }
      }],
      "profile": "reliability:\n  watchdog: 100ms\n  backoff: [1ms]\n",
      "items": [{
        "workflow": "review-flow",
        "goal": "Review the change",
        "seeds": {"goal": "Review the change"},
        "stepMode": false,
        "count": 2,
        "target": "done"
      }]
    }
  }]
}
```

Files land at the same paths used by `workflowDefinitionSource` and
`workflowProfileSource`:

```text
<harness-data-dir>/projects/<project-slug>/profile.yaml
<harness-data-dir>/projects/<project-slug>/workflows/<name>.yaml
<harness-data-dir>/projects/<project-slug>/workflows/<prompt-path>
```

The writer uses `project.ConfigDir`; validation calls the production
`workflowDefinitionSource.Resolve`, which composes production profile loading,
scope resolution, dry-run validation, and prompt inlining.
