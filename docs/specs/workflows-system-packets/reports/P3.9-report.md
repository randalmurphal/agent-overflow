## Implementation notes

- Pane item events retain their immediate patch, survive in-flight overview
  fetches, and schedule coalesced authoritative item/detail refreshes. Refresh
  generations prevent abandoned loads from mutating a reset/reactivated pane.
- Notification activation awaits the workflows-pane retarget/load, so cold and
  post-hydration activations serialize actual navigation rather than launch.
- Retargeting preserves the overview filter. Loads use the union of that filter
  and stack-referenced projects; returning to overview restores filter-scoped
  membership.
- Failed re-enqueue uses `WorkflowReenqueueFailedItem`, reloads the project
  queue, and reports the resulting one-based queued rank. Persisted disposition
  receipts suppress re-enqueue.
- Disposition parks use done-manual actions. Session and persisted receipts
  co-render; keyboard actions are guarded after either receipt class.
- Merge receipts use the backend-returned base and human mode label. A
  `cleanupFailed` receipt remains successful; `workflow:error` owns that error.
- Run rows use human fragments and keep done-awaiting-disposition runs live
  until disposed. The requested `asks — <q>` fragment is absent because the
  summary wire data does not exist, exactly as item 21 directs.
- Queue behavior moved into `WorkflowQueue.svelte` to keep the overview under
  component-size guidance while adding drag feedback and in-flight guards.
- Intake owns its selected project's catalog. Base branch is editable and
  visibly prefilled; untouched/cleared sends `''` for the profile default.

1. Item-state events follow persistence, so the coalesced read is authoritative
   for omitted disposition, timestamp, workspace, branch, and digest fields.
2. `WorkflowListItems(projectId)` reflects a completed re-enqueue and its
   `sortPosition`; sorting queued rows yields the receipt rank.
3. Output envelopes reach the frontend as objects or JSON strings; the newest
   phase envelope with `status: "question"` is the parked question attempt.
4. The sidebar's `projectsLoaded()` gate makes `getProjects()` authoritative at
   initial catalog load; item-bearing project ids are also unioned defensively.
5. A prefill base belongs only to its prefilled project; switching projects uses
   the new catalog default.

   meaning of “prefilled” and “'' when untouched.”
7. Cross-project ordering remains deferred; a per-project-order toast and no RPC
   is correct current behavior.
8. `cleanupFailed` does not change landed success; `workflow:error` reports it.
9. `asks — <q>` is omitted because no summary wire data exists.
