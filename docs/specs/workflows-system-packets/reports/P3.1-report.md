## ASSUMPTIONS

- Migration **v24** was the next free version because the ordered migration
  list ended at v23. The thread rebuild is mechanically derived from the exact
  shipped v23 SQL and changes only the mode CHECK; the work-item rebuild is
  required because SQLite cannot alter its reason CHECK in place.
- Additive partial indexes in v24 are within the migration/store intent: they
  support the new non-empty triage link and phase-thread ownership predicates
  without changing existing index behavior.
- “Current attempt” uses the engine's established rule: newest persisted
  `running` phase if one exists, otherwise the last persisted phase. A send to
  any historical phase thread fails before it can interrupt another attempt.
- A takeover while runner startup is not yet settled fails visibly and leaves
  the attempt/thread intact; retrying after startup is safer than cancelling a
  partially attached phase thread.
- Claude structured output is process-sticky (`--json-schema`), so preserving
  the same logical provider session requires restarting its process on the same
  AO thread/session ref for schema-less steering, then restarting again with
  schema for Complete. Codex continues to use its per-turn output schema.
- Complete and taken-over Resume mark the takeover registration as
  transitioning while holding the thread action lock, then release that lock
  before synchronous runner startup. This blocks concurrent steering without
  deadlocking the send path used by the runner.
- An explicit engine `SetQueue` call owns/reset the transient process-N bound.
  Settings-only active/concurrency updates preserve it; an exhausted bound
  remains effectively paused until another explicit `SetQueue` resets it.
- Item triage is valid only for `needs-human` or `failed` items. Allowing a
  running item to open a full-access second writer would violate the packet's
  failed/parked scope and workspace serial-writer invariant.
- Item triage uses the latest persisted phase's frozen provider/model, falls
  back to the workflow's first frozen phase, and finally uses the ordinary
  remembered/default chat profile when no snapshot model exists.
- Item hand-off runs full-access in the item worktree (project root fallback).
  Project triage uses the project root and the ordinary remembered/default
  runtime profile.
- Triage seeds use store/engine summaries plus `StatusFast` diff counts, never
  raw variables, patches, or gate traces. Every interpolated string is quoted,
  delimiter/control-safe, individually capped, and the aggregate context is
  capped before immediate dispatch.
- A persisted draft triage thread means creation committed but kickoff did not;
  reopening retries its seed. A synchronous kickoff failure deletes the thread
  and clears the item link. This makes the create-before-send crash window
  recoverable without another schema column.
- The project triage singleton is a persisted, unarchived
  `mode='workflow-triage'` thread with no `work_items.triage_thread_id` link.
  Item thread creation and link assignment are one SQLite transaction, so an
  item hand-off can never be mistaken for the singleton after restart.
- P3.1 makes `workflow-studio` legal and hidden only; no studio creator or UI
  flow was added.

## Triage singleton persistence

An item hand-off stores its thread id in `work_items.triage_thread_id` in the
same transaction that inserts the thread. The project-level triage shell has no
item link; `internal/store/threads.go:375` returns the oldest unarchived project
`workflow-triage` thread for which no work item references its id. That durable
absence-of-link discriminator survives process restart without an in-memory
registry.
