Completed 2026-07-13. The packet is implemented end to end: eligible Claude and Codex sessions receive an authenticated first-party `enqueue_workflow_run` MCP tool, tool calls persist confirmation proposals in the calling thread, and users can queue, edit, or dismiss those proposals from the timeline. ## ASSUMPTIONS

1. **Provider capability was verified before design or edits.** Claude Code CLI 2.1.205 accepts `--mcp-config <configs...>` and `--strict-mcp-config`. A real isolated launch used:

   ```json
   {"mcpServers":{"ao-spike":{"type":"http","url":"http://127.0.0.1:43197/mcp","headers":{"Authorization":"Bearer ao-spike-token"}}}}
   ```

   It completed `initialize`, `notifications/initialized`, the streamable-HTTP GET, and `tools/list`; every HTTP request carried the configured bearer header, and the CLI exited successfully after reporting the server ready. Therefore the implementation uses Claude's `type: "http"` plus `headers` shape and additive `--mcp-config` for chat sessions. Existing strict MCP consumers retain `--strict-mcp-config`.

2. **Codex capability was verified against CLI/app-server 0.144.0 and `/home/rmurphy/repos/codex`.** A real isolated `thread/start` used the equivalent TOML shape:

   ```toml
   [mcp_servers.ao_spike]
   url = "http://127.0.0.1:43198/mcp"

   [mcp_servers.ao_spike.http_headers]
   Authorization = "Bearer codex-spike-token"
   ```

   It completed `initialize`, `notifications/initialized`, and `tools/list`, with the expected header on every request. An empty per-thread `mcp_servers` map does **not** suppress inherited global servers because app-server config is deep-merged. A named overlay `{mcp_servers:{ao_spike:{enabled:false}}}` produced zero requests, so existing `DisabledMcpServers` scoping now renders explicit `enabled: false` entries.

3. The first-party endpoint uses `POST /mcp/workflows` on the existing local transport server. It trusts only a constant-time-verified `Authorization: Bearer <transport token>` credential. `X-Agent-Overflow-Thread-ID` is routing metadata and is not treated as authentication.

4. The minimal surface needed by both verified clients is JSON-RPC `initialize`, notification acknowledgement, `tools/list`, and `tools/call`. The endpoint exposes exactly one tool, caps requests at 1 MiB, rejects malformed/multiple JSON values, and returns application validation failures as MCP tool errors.

5. “Interactive threads” means Claude/Codex thread mode `chat` or `workflow-triage`. Plan, design, studio, workflow phase, and unsupported-provider sessions do not receive the tool. This follows the ruling's explicit “normal chat + workflow triage” boundary.

6. The setting is sampled when a provider session starts. Turning it off removes the tool from newly started sessions. An already-running attached session keeps its launch-time MCP entry and can finish a call until that provider session naturally restarts; no mid-flight restart machinery was added, as directed. Claude's live user-MCP reconciliation preserves this launch-time first-party entry.

7. Project inputs resolve by exact database ID first and exact slug second. Archived projects are rejected. Workflow IDs resolve through the effective configured catalog for that project, so normal project-over-shared precedence applies.

8. Proposal seeds validate against the resolved definition input schema both when the tool records the proposal and when an agent-sourced proposal is committed. The required `goal` tool argument remains proposal metadata and is not implicitly injected into `seeds`; definitions that require a `goal` seed must receive it explicitly in `seeds`.

9. Base branch defaults to the project's workflow profile, matching intake. An empty branch remains valid when neither the proposal nor profile provides one. Non-empty values use the existing branch-name validator.

10. Queue/edit/dismiss are local-only because they touch persisted local state and enqueue work. View-only clients render the card and receipt but disable all pending actions with the standard `Local only` title.

11. Proposal actions are serialized in-process. Queue idempotency is also persisted: `(source = "agent", source_ref = proposal ID)` is unique, and a retry recovers the committed work item if the run was created before the card receipt was persisted.

12. Existing `provider:item_event` item upserts are sufficient for live proposal insertion and state changes, so no new event channel was needed.

13. The current E2E mock-provider harness cannot originate an MCP HTTP tool call without modifying forbidden `e2e/src/harness.ts`. No new E2E flow spec was added; direct MCP/backend/component/integration tests cover the feature, and a true tool-call E2E remains a harness follow-up. Both complete existing E2E suites pass twice.

14. No new Go or npm dependency was necessary. The MCP subset is implemented directly.

15. The required post-task review was performed serially because this packet forbids subagents/parallel sessions. Performance/memory, maintainability, architecture, testing, security, and codebase consistency were reviewed. That review added persisted queue idempotency/recovery, ensured edited proposal summaries are persisted, and supplied a conservative timeline size prior.
