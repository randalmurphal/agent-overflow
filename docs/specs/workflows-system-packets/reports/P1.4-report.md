## ASSUMPTIONS

- `gpt-5.6-sol` is the appropriate concrete Codex model for starter agent phases because it is the repository's current built-in Codex default and first fallback model.
- The YAML header path `../workflow.schema.json` means the schema belongs in the parent of each workflow directory: the config root for shared workflows and the project config directory for project workflows. An identical existing schema is reused; a differing existing file is not overwritten.
- The packet's explicit statement that project-scoped `validate` and `list` pass profile bindings to `def.Validate` means list entries should expose `bindingStatus` and typed `findings`; human list output shows the status and finding count.
- Shared operations and project operations with an absent `profile.yaml` are genuinely profile-less and therefore pass nil bindings (`unchecked`). A present malformed profile is always an operational error naming its path.
- Project-scoped resolution validates both the winning project definitions and inherited shared definitions against that project's profile, because either can run for that project.
- The starter accessor's public catalog contains the three product starters. `blank` is a separate minimal scaffold source owned by the CLI, matching the packet's `<starter|blank>` distinction.
- Prompt files are renamed with the requested id so multiple derivatives of one starter can coexist without prompt filename collisions; YAML prompt references are rewritten with the id.
- An existing declared workflow id in the same target scope is an overwrite conflict even when its filename differs, because D1 makes the declared id authoritative. A shared id may still be intentionally shadowed by a project-scoped workflow.
- The config root itself may intentionally be a symlink. Symlinked components below it are rejected for scaffold scopes, and all file creation is additionally confined through `os.Root` directory handles.
- `query-jira-work-items` is a portable profile command name, not a hardcoded executable. A project may bind it to the official Atlassian CLI or another approved host integration.

## Starter phase graphs and bindings

- `build-and-validate`: `implement → validate`; `validate(passed) → done`, `validate(failed) → diagnose`; `diagnose(genuine) → implement [loop max 2]`, `diagnose(flaky|infrastructure) → validate [loop max 2]`, exhausted/unmatched → park. Bindings: checks `build-and-test`; commands none; capacities `validation-slot`.
- `multi-lens-review`: `review(fan-out correctness|maintainability|security → consolidate; approve) → done`, otherwise `review → fix → validate`; `validate(passed) → review [loop max 2]`, exhausted successful review cycle → park, failed → diagnose; `diagnose(genuine) → fix [loop max 2]`, `diagnose(flaky|infrastructure) → validate [loop max 2]`, exhausted/unmatched → park. Bindings: checks `build-and-test`; commands none; capacities `review-workers`, `validation-slot`.
- `poll-jira-and-start`: `query-source → dispatch → done`; dispatch deduplicates by Jira key/update watermark, reuses recorded enqueue effects, and advances the cursor only after all required enqueues succeed. Bindings: checks none; commands `query-jira-work-items`; capacities `jira-poller`.
