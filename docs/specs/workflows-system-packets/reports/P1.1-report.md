## Definition format inventory

Top-level YAML keys:

- `id` — declared stable workflow identity; lowercase letters, digits, and hyphens.
- `name` — human-readable workflow name.
- `description` — optional authoring description.
- `inputs` — workflow seed variables, each with `schema` and optional `optional`.
- `outputs` — run deliverables, each with phase-output `from` and optional `artifact`.
- `phases` — ordered phase list; the first phase is the start node.
- `default_step_mode` — optional intake default that pauses at gates.
- `cleanup` — `manual` or `auto`; omitted means manual.

Per-phase YAML keys:

- `id`, `name` — phase identity and optional display name.
- `driver` — `agent` or `tool`.
- `shape` — `single` (default) or `fan-out`.
- `provider`, `model` — required agent execution selection.
- `prompt` — sibling-relative Markdown prompt file.
- `inputs` — exact consumed references (`goal`, `plan.approach`) with consumer schema and optionality.
- `outputs` — phase output names with schema and optionality.
- `check`, `command` — profile-bound deterministic execution names.
- `resources`, `commands` — profile-bound capacities and additional command grants.
- `capabilities`, `mcp` — structurally declared first-party and MCP grants.
- `access` — `read-only` (default) or `write`; drives workspace derivation.
- `fan_out`, `join` — fan-out units and the required consolidating unit.
- `gate.routes` — ordered first-match routes using `when` plus exactly one of `to`, bounded `loop`, `park`, or `human`.

Predicate keys are the closed set `eq`, `neq`, `gt`, `gte`, `lt`,
`lte`, `in`, `exists`, `all`, `any`, and `not`.

## ASSUMPTIONS

- Per-phase `inputs` are keyed by the exact reference consumed and redeclare the
  consumer-side schema/optionality. This makes D2's bare workflow names and
  namespaced phase outputs directly usable in prompts and gates.
- Omitted phase/unit `access` means `read-only`, following D4.8 and D14.
- Definition files are capped at 1 MiB and prompt files at 4 MiB as defensive
  authoring-input limits; the binding 64 KiB envelope default remains separate.
- `commands` carries named profile command grants in addition to a tool phase's
  primary `command`; `capabilities` and `mcp` are carried structurally for
  later execution/profile policy.
- Scheduler/automation blocks are not part of this workflow document. Spec §11
  defines automations as separate trigger/condition/action configuration whose
  action selects and seeds a workflow.
- Workflow output `artifact: true` distinguishes file deliverables; copying to
  the run artifact store remains engine behavior.
- No binding conflict was found. D4.8/D14 refine spec §9 by naming the authored
  access field; D2a refines the spec's envelope prose and was followed.

## Semantics deferred to the engine

- Ordered predicate evaluation, short-circuiting, optional-absence behavior,
  route selection, predicate traces, and runtime no-match parking.
- Loop-edge counters, feedback injection, exhaustion fall-through, and
  retries-exhausted parking.
- Human gate parking, approve/reject actions, and optional rejection notes.
- Fan-out execution/isolation, fan-in consolidation, and writer serialization.
- Mapping `access` to provider sandboxes and creating/disposing worktrees.
- Capability/MCP authorization and execution, idempotent side effects, and
  profile command invocation.
- Workflow-output artifact capture and cleanup/disposition preconditions.
- Narrative-file attachment, secret masking, and provider-specific envelope
  transport/retry wiring.
- Sub-workflow phases remain deferred post-v1 per the specification and are not
  accepted by this v1 schema.
