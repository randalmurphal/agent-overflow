## Intent

Backend plumbing for the M3 human surface, in four pieces:

1. **Two new thread modes** — `workflow-studio` and `workflow-triage` —
   legal in persistence and engine-owned in creation, excluded from every
   normal thread listing exactly like `workflow` is today.
2. **Take-over of a workflow phase thread** per WHAT-spec §7: sending a
   message into a `workflow`-mode thread interrupts an in-flight turn,
   detaches the run from engine control, allows free-form schema-less
   steering turns, and finishes via **Complete** (one finalize turn with
   the phase's output schema re-attached; its envelope routes through the
   normal gate path) or via the EXISTING discard + re-run machinery
   (`WorkflowResumeItem`).
3. **Hand-off triage threads (D4.2)** — "open a triage thread" for an
   item: a `workflow-triage` thread in the item's worktree, seeded with
   run record, envelopes, diff summary, and typed reason, kicked off
   immediately. Plus the **D4.9 triage-agent thread shell**: open/resume a
   per-project `workflow-triage` thread at the project root. The D4.9
   agent's first-party TOOLS are M4 — this packet ships only the thread
   open/resume plumbing that notifications and the UI will deep-link into.
4. **P2.4 carry-forward (a):** a settings workflow-concurrency update must
   no longer reset a live process-N bound (today `UpdateSettings` forwards
   `maxStarts=0`, silently clearing the bound).

No UI. No disposition (P3.2). No notification senders/digests (P3.3). No
MCP tools, no studio authoring surface (M4 — only the MODE value ships now
so the schema migration happens once).

## Binding design decisions

1. **Migration (one, append-only).** The threads-table `mode` CHECK
   enumerates values, so extend it via the established rebuild pattern
   (see `rebuildThreadsV5SQL` lineage in `internal/store/migrate.go`) at
   the next unused schema version: append `'workflow-studio'` and
   `'workflow-triage'`; preserve every column, index, and trigger
   byte-for-byte otherwise. The SAME migration adds
   `work_items.triage_thread_id TEXT NOT NULL DEFAULT ''` — the persisted
   item↔triage-thread association (decision 5). Extend the existing
   migration tests the way `TestMigrationV22CreatesWorkflowPersistence`
   asserts columns.
2. **`internal/threadmode` stays the single source of legal values.** The
   new modes join `workflow` and `discussion` as saga-owned: rejected by
   `ValidateCreate` and `ValidateSet`, absent from `ManualSelectionModes`
   and `PostCreationModes`. Add a package-level way to ask "is this mode
   hidden from normal listings" (the set {workflow, workflow-studio,
   workflow-triage}) so exclusion has ONE definition — then route the
   existing backend listing exclusions (the P2.4 mechanism that hides
   `workflow` threads from user-facing listings, search, and pickers)
   through it. No scattered string literals. Update the package AGENTS.md.
3. **Take-over detach is an engine state, not a side channel.** New typed
   reason `ReasonTakenOver Reason = "taken-over"` parking the item at
   `needs-human` (FSM rules already require a reason there). Detach must:
   stop the runner's watchdog/timers for the attempt, release the item's
   resource-semaphore holds, keep the worktree and the provider session
   untouched, and persist the park (crash → startup rebuild lands the item
   back at needs-human(taken-over), same as any other park). Emit the same
   `workflow:*` event shape other parks emit.
4. **Take-over entry is the send path, not a new button-RPC.** An
   interactive send into a `mode='workflow'` thread whose item has a live
   or parked attempt: (a) if the turn is in-flight, interrupt it first via
   the existing stop/interrupt machinery and wait for the yield; (b) mark
   the item taken-over (decision 3); (c) the send itself runs as a normal
   free-form turn with NO output schema, through the runner's
   session/schema registration seam (P2.4 carry-forward (b)) so triage
   ownership and turn accounting stay correct — a free-form send to a
   parked workflow thread whose session died must start a fresh session on
   the same thread/worktree instead of erroring (today's hard error was
   correct only until this flow existed). Exception per §7: an item parked
   on a `question` envelope keeps its existing answer path
   (`WorkflowAnswerQuestion`) — sending into the thread while parked on
   question is still take-over, but the question answer RPC itself must
   keep working unchanged.
5. **Complete = `WorkflowCompleteTakeover(itemID)`.** Valid only from
   needs-human(taken-over). Runs ONE finalize turn in the same thread and
   session with the phase's output schema re-attached (same registration
   seam as a normal phase turn, same envelope post-validation and retry
   feedback); the resulting envelope routes through the normal gate path
   as if the phase finished on its own — "one contract, one schema" (§7).
   A finalize turn that still fails envelope validation after the runner's
   normal retries re-parks at taken-over (not agent-error): the human is
   already driving. Discard + re-run needs NO new RPC — assert
   `WorkflowResumeItem` re-runs the phase fresh from a taken-over park
   (worktree reuse/recovery semantics from P2.6 apply unchanged).
6. **Hand-off RPC: `WorkflowOpenTriageThread(itemID)`.** Open-or-return:
   if `work_items.triage_thread_id` names a live thread, return it;
   otherwise create a `workflow-triage` thread in the item's worktree
   (project root when the item has none), persist the association, seed
   it, and kick it off — the seed (run record, envelope summaries, diff
   summary, typed reason; NEVER raw variables/gate traces per the
   no-internals rule) is sent as the first user turn so the agent starts
   immediately. Compose the seed from data the store/engine already has;
   plain prose + fenced diffs, no JSON dumps. Thread title is set
   deterministically from the item (no auto-title generation — same
   exemption workflow threads use in `app_send.go`).
7. **Triage-agent shell: `WorkflowOpenTriageAgent(projectID)`.**
   Open-or-return the project's singleton `workflow-triage` thread at the
   project root (no item association; distinguish it from hand-off threads
   by its empty item linkage, and persist the association the same
   queryable way — an ASSUMPTIONS-documented mechanism on the project row
   or a store query by (project, mode, no-item) is acceptable if it
   survives restart). No seeding beyond a short fixed framing message; no
   tools (M4). It exists so P3.3's notifications and P3.4/P3.6's UI have a
   stable target.
8. **Carry-forward (a) fix.** `WorkflowSetQueue`'s live process-N bound
   must survive an unrelated settings update: the settings path may no
   longer blindly forward `maxStarts=0`. Give the engine command an
   explicit "leave the bound unchanged" input (sentinel or separate
   setter — your call, documented) and route the settings update through
   it. A user-initiated queue update that INTENDS to clear the bound still
   can.
9. **Studio threads: mode value + exclusion only.** Nothing creates
   `workflow-studio` threads in this packet; the value becomes legal (one
   migration) and excluded (decision 2). Do not build studio flows.
