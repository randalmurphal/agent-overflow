## Context you must know first

- The harness: `make harness` boots the real app headless with mocked
  providers on an isolated data dir; `make e2e` builds and runs the
  Playwright suite in `e2e/`. Read `e2e/AGENTS.md` and
  `docs/architecture/agent-harness.md` first, then the three existing
  spec files — they are the exemplars for every pattern you need:
  - `e2e/tests/harness.spec.ts` — UI-driving specs: `page.goto
    (harness.url)`, wire-event waits + auto-waiting locators,
    frame-accurate stepping via `HarnessMockCommand`.
  - `e2e/tests/workflows.spec.ts` — workflow engine driving: scenario
    authoring (`HarnessSetScenario` with `doneResult`/`questionResult`
    envelopes), workflow YAML shapes (single/two-phase, human gate,
    watchdog profile), `WorkflowEnqueueItem`, `workflow:item-state`
    waits, waitSignal-held mocks.
  - `e2e/tests/notifications.spec.ts` — `HarnessNotify` degraded-send
    (`rejects.toThrow(/method_error: OS notifications are
    unavailable/)`) still emits `notification:activated`; cold
    activation precedes `page.goto` to cover transport replay + the
    pre-hydration queue.
- Seeding: `HarnessSeed` (`app_harness_seed.go`,
  `app_harness_workflows.go`) creates projects/threads and — per
  project — workflow `definitions` (YAML + prompt files), a `profile`,
  and `items` with `target: queued | needs-human | done` (driven
  through the REAL engine + mock provider; the active scenario
  determines the parked `reason`). Queued targets require the queue
  paused to stay queued deterministically — the seed handles this;
  keep `WorkflowSetQueue` in mind for your own live-flow specs.
- The M3 UI shipped in P3.4–P3.6 (all merged on `workflows-system`):
  the workflows pane (`frontend/src/lib/components/workflows/*`,
  stores `workflowsPane.svelte.ts` / `workflowData.ts` /
  `workflowsSidebar.svelte.ts`), sidebar surfaces
  (`components/sidebar/WorkflowsFooter.svelte`,
  `WorkflowsSection.svelte`), deep links
  (`stores/notificationActivationQueue.ts`), and the review companion
  (`PaneHost.svelte` workflows branch, `reviewPane.svelte.ts`).
  Existing `data-testid`s cover most surfaces (`wf-*`,
  `workflows-footer`, `sidebar-workflows-button`,
  `workflows-footer-attention`, `workflows-section`,
  `workflow-sidebar-run`, …) — read the components for the full
  inventory before inventing selectors.
- Engine vocabulary: states queued/running/needs-human/failed/done/
  cancelled; parked reasons include gate, question, stalled,
  disposition; `state === 'done' && !disposition` = awaiting
  disposition (stays listed, neutral); done + non-empty disposition =
  resolved (drops off sidebar). Attention (amber counts) = needs-human
  + failed only.
- Disposition RPCs: `WorkflowMergeItem`, `WorkflowCreateItemPR`,
  `WorkflowDiscardItem` (P3.2). Gate/question: `WorkflowResolveGate`,
  `WorkflowAnswerQuestion`. Queue: `WorkflowSetQueue`,
  `WorkflowReorderQueue`, `WorkflowRemoveQueuedItem`,
  `WorkflowCancelItem`.

## Intent

Playwright specs that drive the REAL SPA through every M3 workflow
surface on harness seeds — the UI layer that `workflows.spec.ts`
deliberately skipped. Each surface below gets its own spec file; the
listed scenarios are the REQUIRED minimum, not a ceiling. Where a
scenario needs a state the seed targets can't reach directly, drive it
live with scenarios + RPCs the way `workflows.spec.ts` does.

1. **Sidebar (§6, §11)** — `e2e/tests/workflows-sidebar.spec.ts`:
   footer with no runs (present, no badge) and with parked runs (amber
   count; click → pane at overview); per-project section roll-up and
   expanded rows ordered needs-you → failed/running → queued → done;
   done-awaiting-disposition renders neutral/dim and does NOT count as
   attention; row click opens the pane at that run; cancelled runs
   drop off the section; §6.3 exclusion — after a workflow run
   creates phase threads, they never appear in the sidebar thread
   list or search, while the run's phase thread still opens from run
   detail.
2. **Pane navigation (§§2–4)** — `e2e/tests/workflows-pane.spec.ts`:
   overview renders definitions and the Up-next queue; drill overview
   → workflow → run and back via breadcrumbs; queue pause toggle
   reflects and flips `workflowQueueActive`; queued-row cancel arms
   (`cancel?`) then cancels; page reload restores the pane at the
   same stacked level (persistence).
3. **Run detail + action flows (§5)** —
   `e2e/tests/workflows-run-actions.spec.ts`: human gate parks →
   action row renders → Approve via the UI button → run completes
   (assert the transition in the DOM, not just the wire); question
   parks → answer via the UI → same-session continuation to done;
   stalled (watchdog profile) → parked row shows the stalled
   treatment and its recovery affordances; done-awaiting-disposition
   → disposition actions render → Discard via the UI resolves the run
   (receipt rendered, run drops from the sidebar).
4. **Sweep (§5, §9)** — in the run-actions file or its own: seed ≥2
   parked runs, enter the needs-attention sweep, j/k advances between
   parked runs, resolving the last one lands on all-clear.
5. **Intake (§7)** — `e2e/tests/workflows-intake.spec.ts`: with the
   queue paused, open intake from "+ New run", pick a workflow, fill
   the goal, submit; the queued row appears in Up-next and the
   sidebar; validation blocks an empty goal.
6. **Deep links (§10)** — `e2e/tests/workflows-deeplinks.spec.ts`:
   `HarnessNotify` with a `workflow-item` target (cold, before
   `page.goto`) opens the workflows pane at that run inside the
   sweep; a dead `workItemId` shows the error toast and lands on
   overview; a `workflow-triage-agent` target opens the project's
   triage thread in a pane (and that thread stays out of the sidebar
   list, §6.3).
7. **Review companion (§5.7)** — in the pane or run-actions file: a
   done run's "Open full review" (`wf-open-full-review`) renders the
   review companion beside the workflows pane
   (`data-companion-source-pane-id="workflows"`); closing the
   workflows pane closes the companion. The mock provider writes no
   files, so assert the companion chrome + its empty/loaded state,
   not diff rows.

## Binding decisions (do not re-litigate; verify cited facts before relying on them)

1. **One spec file per surface** as named above; keep each under ~500
   lines; shared helpers (workflow YAML builders, scenario/envelope
   helpers, seed wrappers) go in `e2e/tests/workflows-helpers.ts` —
   extract the existing private helpers from `workflows.spec.ts` into
   it and import them from BOTH files rather than duplicating
   (`workflows.spec.ts` keeps its assertions byte-identical; only its
   imports may change).
2. **Never sleep; never assert wall-clock text.** Waits are wire
   events (`workflow:item-state`, `harness:mock`,
   `provider:turn_completed`, `notification:activated`) plus
   Playwright auto-waiting locators. Do not assert elapsed-time
   strings ("14m"), cost strings, or anything time-derived; assert
   their container's presence instead.
3. **Selector discipline.** `page.getByTestId` with the shipped
   `data-testid`s. Where a required assertion has no testid, ADD one
   to the component — additive attribute only, no markup or logic
   changes — and list every addition in the report. Text selectors
   only for user-visible copy that is itself the assertion.
4. **Backend setup goes through RPCs; the UI is driven only for the
   behavior under test.** One exception per flow: the mutating action
   the spec exists to prove (Approve, answer, discard, intake submit,
   pause toggle, cancel) MUST go through the UI, not the RPC.
5. **App-bug protocol.** If a required scenario fails because the
   shipped UI misbehaves against the UI-SPEC, do NOT bend the spec to
   match the bug and do NOT fix app code. Write the spec you believe
   correct, mark nothing skipped, and go BLOCKED with the repro
   (spec file + failing assertion + what the UI did). Surfacing these
   is this packet's purpose.
6. **Remote view-only posture (§12) is OUT of scope.** The harness
   page connects over loopback; the posture is unit-covered from
   P3.6. Do not simulate non-loopback peers.
7. **Determinism.** The full suite must be order-independent and
   reset-clean (the fixtures reset per test — leave it that way). Run
   `make e2e` TWICE from the final tree; both runs green; paste both
   tails. A spec that flakes is not done.
8. **No new harness RPC surface.** If a scenario genuinely cannot be
   driven with the existing `Harness*` RPCs + seed targets + bound
   methods, that is a scope question — BLOCKED, not an
   `app_harness_*.go` edit.

## Scope Amendment 1 (unblock ruling, 2026-07-12)

Both reported discrepancies were verified as genuine shipped bugs.
The adjudicator fixed them on the base branch, and the fixes are now
merged into your lane branch:

1. **Sidebar never populated.** `WorkflowListItems("")` returned no
   rows — `internal/store/work_items.go` treated an empty ProjectID as
   a literal match (`WHERE project_id = ''`), so the sidebar store's
   single app-wide fetch loaded nothing. Fixed store-side: an empty
   ProjectID now lists every project (store test added). The footer
   badge and project sections populate from parked seeds now.
2. **Up-next cancel used the wrong RPC.**
   `WorkflowOverview.svelte`'s `cancelQueued` called
   `WorkflowCancelItem`, which the engine rejects for queued items
   (cancel is running-only). Fixed to `WorkflowRemoveQueuedItem`; the
   toast copy is now "Removed from queue — record kept, nothing was
   provisioned" and the error copy "Could not remove the queued run."
   The armed `cancel?` interaction is unchanged.

Rulings for your specs:

- The footer/section scenarios should pass unchanged against the fixed
  tree.
- Your ordering spec's setup calls
  `harness.rpc('WorkflowCancelItem', cancelled.id)` on a QUEUED item —
  the same engine constraint rejects that; it is a spec-side setup
  error, not a second app bug. Use `WorkflowRemoveQueuedItem` to
  retire a queued seed (it lands cancelled/interrupted and stays
  excluded from the sidebar), or drive the item to running first if a
  scenario needs a true cancel.
- Specs that exercise the queued-row `cancel?` UI path should assert
  the row disappears after confirmation; do not assert toast copy
  unless the copy itself is the behavior under test.

Continue from your dirty tree; your completed work and the helper
extraction stand. Finish the work plan and run the final-tree gates
per the packet (gate 8 twice). All other rules stand.
