## Binding design decisions

1. **Singleton + stack are the pane's identity.** At most one workflows
   pane; every open path goes through `openWorkflowsPane`. Stack levels:
   `overview › workflow › run` + terminal `all-clear` (§2.2, §5.4).
   Esc/Backspace pop; Esc consumes transient state first (armed confirm
   → open dialog → pop) and NEVER closes the pane at depth 0. Slide
   transitions honor `prefers-reduced-motion`.
2. **Data loading is fetch-on-navigate + event-patch, bounded.** Core
   principle 4 applies: no in-memory event store, no full-history cache.
   Overview/workflow levels use `WorkflowListItems` (per project; "All
   projects" fans out over the known projects and merges) +
   `WorkflowListItemCosts` + `WorkflowListDefinitions`. Run detail uses
   `WorkflowGetItem` on push and refetches on that item's
   `workflow:item-state` events (each event carries no row data — it is
   a refetch trigger; patch the state/reason optimistically from the
   event, then reconcile). `workflow:phase-state` refetches only an open
   run detail. `workflow:queue-state` patches the header. Heavy fields
   (diff text, digest upgrade) load on demand and are dropped when the
   level pops.
3. **`workflow:error` is user-facing state (core principle 5):** toast
   it (terse, deduped by itemId+message, no internals). If the item is
   visible, its row/detail also reflects the parked state via the
   accompanying item-state event.
4. **R1/R2 are enforced in one place each.** A single
   `workflowRunSignal.ts` classifier (pure, table-tested like
   `threadStatusPill.ts` — reuse its dot/pulse/`status-glow-warning`
   class conventions) maps state+reason → {signal, label, tone}: amber
   ONLY needs-human(gate|question|…all reasons), red ONLY failed,
   everything else typographic; done-awaiting-disposition (state done,
   empty disposition receipt) is NEUTRAL. R2: snapshot, seeds, envelopes,
   gate traces, budget JSON never render; the string "variables" never
   appears in copy. Metadata fragments are `·`-separated per R4.
5. **Evidence blocks (§5.3), data sources:**
   - Digest: item.digest two-row block (§5.2); refreshed when the async
     upgrade re-emits item-state.
   - Diff (gate, done): `GetBranchBaseDiff(threadID, item.baseBranch)`
     using the newest phase attempt with a threadId; parse with the
     existing `utils/diff.ts`; render the §5.3 file list `path +a −d`
     with in-place hunk expansion. No ReviewPane wiring (P3.6).
   - Checks row: derive from the run's check-phase attempts (phase id,
     status ✓/✗, duration from startedAt/endedAt). Identify check phases
     from the frozen definition snapshot (`item.snapshot`, detail-only)
     WITHOUT rendering the snapshot. If the snapshot does not cleanly
     distinguish check phases, omit the checks row and document the gap
     as an assumption — do NOT invent heuristics over phase ids.
   - Phase list (running, §5.3/§5.6): all attempts from detail.phases,
     one row per attempt, openable when threadId is set (existing
     open-thread-pane machinery). Live-activity line for the running
     phase: reuse the sidebar's live-status projection
     (`threadStatuses.svelte.ts` / `eventsThreadRows.ts`) keyed by the
     phase threadId if those projections exist for hidden-mode threads;
     if they don't, render current phase + elapsed only and document as
     an assumption. Do not build a parallel live-status pipeline.
   - Outputs (§5.5): detail.artifacts named values + file rows; files
     open via the existing preview/system-opener paths.
   - Costs: detail usage for `$` fragments in run detail; the
     `WorkflowListItemCosts` map for list rows; all-clear summary sums
     the session's resolved items client-side.
6. **Take-over and hand-off open threads; they do not build UI.**
   `t` on gate/question opens the newest phase thread as a normal
   thread pane + toast ("Turn interrupted — the review thread is yours
   to steer" — the actual take-over binds on SEND, which the backend
   already handles). `t`/Continue-with-agent on failed/done calls
   `WorkflowOpenTriageThread(itemID)` and opens the returned thread
   pane; run resolves in place per §8.2. Overview "Triage" calls
   `WorkflowOpenTriageAgent(projectID)`; "+ New workflow" and workflow
   detail "Edit" call the P4 preamble's `WorkflowOpenStudioThread` —
   all three just open the returned thread as a pane.
7. **Action → RPC mapping (exact):** gate Approve →
   `WorkflowResolveGate(id, "approve", "")`; Request changes →
   `WorkflowResolveGate(id, "reject", note)` (inline optional note,
   Enter commits) — verify the decision strings against
   `app_workflow.go` before assuming; question answer/digits →
   `WorkflowAnswerQuestion`; failed Re-enqueue with guidance →
   `WorkflowResumeItem(id, "")` (the backend already carries the
   diagnosis; verify the targetPhase contract in `app_workflow.go`);
   done Merge → `WorkflowMergeItem`, Create PR → `WorkflowCreateItemPR`,
   Discard → `WorkflowDiscardItem` (danger, armed confirm); running
   Stop / queued-strip cancel → `WorkflowCancelItem` (armed confirm per
   §4.2); queued Remove → `WorkflowRemoveQueuedItem`; reorder →
   `WorkflowReorderQueue`. Disposition receipts render from the receipt
   JSON (§5.3 done row: merged receipt kv block / PR block).
8. **The queue toggle uses the settings path, not `WorkflowSetQueue`.**
   `WorkflowSetQueue` replaces the transient process-N budget (P3.1);
   the pane toggle must not clobber it. Toggle → `UpdateSettings`
   (patch `workflowQueueActive`), state → `workflow:queue-state` events
   + settings snapshot. Slots-in-use = count of running items across
   projects (derived; no new RPC).
9. **Intake:** dialog on the existing Modal primitive (exemplars:
   `AddProjectModal`, `ThreadFromPRDialog`), fields exactly §7.1 order;
   invalid definitions greyed with their first validation error,
   selection blocked; typed seed fields from the P3 preamble's `inputs`
   (string/text, multiline/textarea, enum/select, boolean/checkbox,
   number/number, `format: path` file-pick); step-mode checkbox
   defaulting from the definition; footer `Queue — position N` from
   `predictedQueuePosition`. Seeds submit as a `{name: value}` JSON
   object — verify against how the engine reads `work_items.seeds`
   before assuming. The dialog accepts a full prefill object. Chat
   confirm card (§7.2): a presentational `chat/` component (heading,
   summary line, Queue it / Edit / Dismiss; Edit opens the prefilled
   dialog) with unit tests, mounted in the chat timeline ONLY if a
   clean custom-item-kind seam already exists there; if mounting would
   require provider-parsing or item-pipeline changes, ship the component
   unmounted with its contract documented — M4 owns the producing tool
   and will wire it. Never a silent enqueue.
10. **Sweep membership and order:** parked set = needs-human (all
    reasons) + failed + done-with-empty-disposition, app-wide honoring
    the overview project filter, ordered oldest-parked first by
    `endedAt`, wrapping (§5.4). Session-resolved runs render receipts,
    stay in the cycle, are skipped by auto-advance. All-clear summary
    counts this session's resolutions by kind + summed cost.
11. **Keyboard (§9 verbatim):** register pane-scoped through the
    existing keybinding/command registries; suppressed while any text
    field has focus; digits pick suggested answers; `a`/`r`/`t` follow
    the per-state table. Palette/command-registry conventions from the
    existing pane commands apply.
12. **Tests:** vitest for every store/classifier/reducer (stack ops,
    sweep cursor + wrap + skip, filter fan-out merge, signal classifier
    table incl. done-awaiting-disposition neutrality, event → patch
    reducers, action → RPC dispatch with mocked bindings, intake
    validation gating, keyboard scoping incl. Esc precedence). Component
    tests where the repo already tests components (see `PaneHost.test.ts`
    et al.) for: pane singleton reuse, level push/pop rendering, action
    row per state, dialog field rendering from a listing fixture. Go
    tests for the preamble (usage on detail, cost map query, catalog
    shape + inputs distillation).

## Scope Amendment 3 (unblock ruling, 2026-07-12)

runs are indistinguishable from done-awaiting-disposition at list

   UPDATED — never deleted, never weakened — to assert the new
   contract at equal rigor: disposition round-trips in summaries,
   digest still blanked.

   awaiting disposition (sweep member, "to dispose"); non-empty parses
   to the receipt for list/history rendering. Full receipt detail
   views still come from `WorkflowGetItem`.

No other rule changes; Amendments 1–3 compose.
