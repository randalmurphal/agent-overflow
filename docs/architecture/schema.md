# SQLite Schema

The executable schema is the squashed baseline in
`internal/store/schema_v1.go` plus the forward-only migrations in
`internal/store/migrate.go` and `internal/store/migration_v*.go`. Those files
win if this summary disagrees. See [sqlite-store.md](sqlite-store.md) for
connection, migration, restore, trigger, and query contracts.

## Data classes

SQLite has three distinct responsibilities:

| Class | Meaning |
|---|---|
| Provider-history cache | Conversation history and derived render data can be rebuilt from provider session files. Restore and retention may replace or remove it under their documented guards. |
| Application records | Projects, settings, workflow records, drafts, and usage are durable application data. Their accessors define their lifecycle. They are not evidence that SQLite is an event store. |
| Authoritative state | Identity, accepted-message queues, transfer ownership, remote command acceptance, and notification ownership have no provider-history replacement. Whole-store snapshot restore handles them deliberately; history retention and generic cleanup must not treat them as cache rows. |

The phrase "SQLite is a history cache" applies to provider history. It does not
make every row disposable.

## Provider history

| Tables | Ownership and key constraints |
|---|---|
| `threads`, `turns`, `message_anchors` | Conversation metadata, thread-scoped turns, and provider message correlation. `threads.history_rev` and `history_epoch` invalidate client replicas. `threads.fork_preparing` keeps incomplete forks listed but unavailable until provider wiring is durable. `threads.delete_claim` (v155) is the operation id of a delete that claimed the thread and has not yet gone ahead (`ClaimDeleteFamily`, which claims a whole family in one transaction, a worker only while its owner still owns it, and refuses one another delete holds; partial index `idx_threads_delete_claim`): the row stays listed, and every write that would run, move or change it refuses it (`checkThreadNotDeleting`). A refused delete clears its claims in one transaction (`ReleaseDeleteClaim`), and the boot clears every claim no delete committed (`ReleaseUndecidedDeleteClaims`). `threads.deleting` marks a thread whose delete went ahead: `CommitDeleteClaim` sets it on the claimed family in one transaction; `owned_threads` leaves it out from then on, `DeleteThreadPaced` sets it too and removes the row in its last transaction, and the app completes a marked thread at boot (`ListPendingThreadDeletes`, partial index `idx_threads_deleting`). Mode `holder` is a hidden thread that keeps rows pointer forks read after the thread that showed them changed, reverted or deleted them ([sqlite-store.md](sqlite-store.md#ownership)); `owned_threads` leaves holders out, and `trg_thread_fork_lineage_release` sets `deleting` on one no fork reads. `fork_source_thread_id`, `fork_cut_turn_index` and `fork_cut_item_index` record a pointer fork's immediate source and cut; a holder's `fork_source_thread_id` names the thread whose rows it took, and a retired thread's is empty; `fork_source_title` is the source's title when the fork was made. `threads.newest_turn_error_at` and `newest_turn_error_turn` are the Failed pill's write-time aggregate, maintained by the turn-error triggers, which count the rows a pointer fork inherits; a fork's writers recompute it when which rows it inherits changes. `threads.placement` (`owned`, `grouped`, `standalone`, v154) is whether the sidebar shows the row: a CHECK makes it `grouped` exactly when `group_id` is set, `owned` (no sidebar row; `catalogThreadClause`) is written only for a thread with a spawn link, a local spawn or a paired computer's link receipt (`spawnLinkSQL`), and `trg_thread_placement_spawn_gone` (v155) makes an owned thread of a project `standalone` when its link is deleted: its owner's delete deletes it first, so the trigger reaches one whose owner moved to another computer and left its cache here; `trg_thread_placement_link_gone` and `trg_thread_placement_link_deleted` (v158) do the same when a link receipt ends, its flag cleared, its thread detached or the receipt deleted, unless a local spawn also links the thread. A helper stays owned, and `SetThreadPlacement` refuses a thread outside every project ([standing-agents.md](../specs/standing-agents.md#owned-workers)). `attention_kind`, `attention_reason` and `attention_at` (v154) are the attention flag its agent raised with `thread_attention`, written only by `SetThreadAttention` and `ClearThreadAttention`; `attention_at` is a read target, so a read clears the flag as it clears a completion ([standing-agents.md](../specs/standing-agents.md#attention)). `spawn_instructions` (v155) is written once, at creation: what the spawn that made the thread appended to its system prompt for its whole life (a fork copies and extends it, a transfer carries it). `spawn_level` (v155) is the sub-thread level a paired computer's owned spawn or ask carried, written at creation and set to 0 by a transfer's commit; `SubThreadLevel` adds it beneath the thread only while the thread is owned or an ask copy, so a group or a standalone row ends it and Remove from Sidebar restores it ([agent-thread-tools.md](../specs/agent-thread-tools.md#sub-thread-depth)). `archived` has one writer, `setThreadArchivedTx`, whose unarchive withdraws the archives owed for the thread's remote spawns (`supersedeOwedArchivesTx`). Narrow lifecycle columns such as fork preparation, import provenance, live todo, group membership and placement, and worktree setup state have dedicated writers and are omitted from broad updates. |
| `items` | Mutable timeline overlay keyed by `(thread_id, id)` and ordered by `(thread_id, turn_index, item_index)`. `summary` is the always-loaded raw preview. `parent_id` links nested work; `completion_of` links completion siblings to launches: the ending one, and a background agent's `parked` stops (`status = 'parked'`). `rev` is the owning thread's `history_rev` when the row's read result last changed (imported rows project -1). `find_text` (and `import_history_items.find_text`) is thread find's candidate text (`internal/store/find_candidate.go`): derived, served by no read, NULL until filled; a find computes an unfilled row's as it reads it. Migration v157 (`user_find_text`) unset it on the top-level user rows, through `idx_items_user_text`, when their candidate text gained what the row shows beyond its text as written (an agent message's header line, a provider agent message's first line with its white space collapsed, a report's decoded data); its deferred phase refills them with v150's backfill. Nested user rows and `import_history_items` keep the candidate text an earlier build filled. Item triggers maintain history stamps, subagent anchor cards, payload collection, import guards, and background liveness. |
| `payloads`, `payload_chunks` | Heavy content keyed by `(thread_id, id)`. Metadata and capped preview spans may ride list reads; base data, chunks, and full spans load on demand. Span blobs are versioned render caches. |
| `thread_fork_lineage`, `thread_fork_hidden`, `thread_fork_walked` | Pointer-fork reads ([sqlite-store.md](sqlite-store.md#pointer-forks)). `thread_fork_lineage` has one row per ancestor a fork reads through, keyed by `(thread_id, depth)`, with the ancestor and the cut for that level; a holder takes a level of its own. `thread_fork_hidden` lists the inherited ids a fork does not show: rows it copied, reverted or deleted, rows fork creation excludes (live background launches, what an item cut leaves out, and what hangs off either), rows an ancestor added or moved below the cut later, and for a holder the ids it holds, so a row the thread it took them from writes later under one of those ids stays out of the forks' history. `thread_fork_walked` lists, per thread, the anchors whose subagent card the thread and every thread that reads it walk instead of reading the stamp of the level that holds the anchor, because they show other rows under it than that level counts (`internal/store/fork_walked.go`); rows are only added, and a retired thread keeps them. All three cascade with the fork's thread row. |
| `shown_history_fix` | At most one row (`id = 1`), which exists only inside a migration's data fix transaction and never commits (`fixShownHistoryTx`). While it exists the pointer-fork payload guards and the item update guard pass the fix's writes, so the fix reaches every copy of the data: a row or payload a fork shows and a holder's ([sqlite-store.md](sqlite-store.md#ownership)). |
| `payload_snapshots`, `payload_snapshot_refs`, `payload_snapshot_chunks`, `payload_snapshot_edits` | Retired. Migration v120 copied every borrowed payload graph back into the payload rows that referenced it and emptied the tables; nothing reads or writes them. |
| `import_history_chunks`, `import_history_items`, `import_history_payloads` | Immutable imported history. Imports use content-addressed chunks. Chunk-local composite keys keep item and payload identity together. Chunks with `sealed:` ids hold local rows the removed background sealing moved; the history repair folds them back ([sqlite-store.md](sqlite-store.md#history-repair)). |
| `thread_import_chunks`, `thread_import_item_overrides`, `thread_import_state` | Ordered mapping of chunks into a thread, explicit mutable-overlay hides, and provider refresh provenance. Triggers reject gaps, overlaps, and implicit shadowing. Each reference copies its chunk's turn range on attach, and `trg_import_history_items_turn_range` keeps a chunk's range bounding its rows, so a turn read may skip every reference whose range excludes the turn. |
| `edit_file_snapshots` | Gzip-compressed new-side file snapshots for diff expansion. They cascade with their payload and remain cache content: readers verify them against the requested patch. |
| `subagent_aggregates` | One row per local subagent anchor keyed `(thread_id, item_id)`, cascading with its item: the card and tray values a read serves, the positions the incremental rules need, and `state` (clean, dirty, readTime). A local item projection merges a clean row's public values into the served `meta` (`subagentServedMetaSQL`); stored `items.meta` never holds them. A pointer fork reads an inherited anchor's clean row at the level that holds it when that row describes what the fork shows (`inheritedStampReads`). A holder keeps the clean rows that move with its items, and nothing recomputes them. `idx_subagent_aggregates_dirty` finds the rows a recompute owes. |
| `subagent_aggregate_backfill` | The threads whose subagent anchors predate the write-time cards. Migration v121's deferred phase stamps them in paced batches and deletes a thread's row with its last unstamped anchor; until then reads walk that thread's unstamped anchors. |
| `agent_end_backfill` | The threads that held an open row under a parent when migration v124 ran, with that time (`opened_at`). v124's deferred phase settles the open rows of each of a thread's ended agents by the live path's agent end rule, one agent per paced write, and deletes the thread's row once none is left to settle ([turn-lifecycle.md](turn-lifecycle.md#agent-owned-rows)). |
| `pending_background_task_terminals` | Claude terminal observations awaiting their chat-side completion sibling. Lifecycle gates consult these rows; tray display retains the launch until the sibling lands. |
| `provider_thread_cost` | Provider-reported cumulative cost estimate for the current `session_ref`. It is replaced in place and ignored when the thread points at a different provider session. It is not a per-turn `usage_ledger` entry. |

`timeline_items` and `timeline_payloads` are logical views over the mutable
overlay, immutable import chunks and a pointer fork's inherited rows.
`timeline_payload_chunks`, `timeline_edit_file_snapshots` and `timeline_turns`
add the inherited append chunks, edit snapshots and turn rows. Ordered, limited,
and recursive item reads use the physical arms from `timeline_arms.go`; see
[sqlite-store.md](sqlite-store.md#logical-history).

`thread_search_rows`, `thread_search`, `thread_search_build` are the agent
search index. `thread_search` is a contentless FTS5 table, so no message text is
stored twice; `thread_search_rows` maps each FTS rowid to its thread, item and
arm (`item` or `import`), and snippets are produced in Go. Settled message text,
tool-call summaries and thread titles are indexed by the write that settles
them; streaming rows are not. Hidden modes are excluded at query time by joining
`owned_threads`, so a mode change needs no reindex. `thread_search_build` holds
one progress row while the background build walks the existing corpus; restore
drops all three and inserts a fresh progress row, because the index is derived
and FTS5 shadow tables cannot be copied row by row.

`owned_threads` is the ownership-filtered thread view. It applies the latest
non-canceled transfer epoch so catalogs and execution checks do not recover a
conversation whose ownership moved to another computer, and it leaves out a
thread whose delete went ahead (`threads.deleting`) and a holder, so listings,
search, transfers and fork admission never reach a partly deleted thread or
the kept history of a deleted one.

## Application records

| Tables | Ownership and key constraints |
|---|---|
| `projects` | User-defined repository grouping. `path` and immutable filesystem-safe `slug` are unique. `worktree_setup` is strict JSON owned by `internal/worktreesetup`. `repository_id` is the host-scoped forge identity; `identity_source` privately detects an origin change before reusing a verified ID; retired `remote_url` and `root_commit` remain empty; `identity_error` is the last failed read of it, kept beside the last good identity. Legacy workflow queue columns remain physically present but have no readers or writers. |
| `thread_groups` | Named per-project sidebar groups. Membership is `threads.group_id` with `threads.placement` `grouped`; deleting a group ungroups its threads and clears their pins. A group has no pin; a grouped thread carries its own, cleared whenever it joins or leaves a group. A name is unique per project, case-insensitively, so resolve-or-create by name has one answer. |
| `codex_developer_instructions` | The SHA-256 digest of the developer instructions a thread's Codex thread last received, keyed by thread and naming the Codex thread (`session_ref`) it describes, so a thread repointed at another Codex thread reads as having no record. A resume whose composed instructions differ, or that finds no record, injects them once ([codex-wire.md](../references/codex-wire.md#developer-instructions-on-a-resumed-or-forked-thread-verified-01621)). Cache content: a lost row costs one repeated injection. An in-place revert deletes the row; cascades with the thread and is cleared from a holder. |
| `thread_pull_requests` | The open PR a thread's linked worktree was last seen with, one row per thread, for the merged-PR worktree cleanup ([forge-transport.md](forge-transport.md#merged-pr-worktree-cleanup)): forge, host, project, number, URL, GitHub node id, branch and worktree path, then `merged_at`, `removal_failed_at` once its threads were told a removal git refused (so a retried removal tells them once) and, once acted on, `handled_at` with `outcome`. Recording another open PR re-arms the row; recording the same one does not, so a handled PR is acted on once. `idx_thread_pull_requests_pending` holds the unhandled rows and `idx_thread_pull_requests_pr` serves the Pull requests page's lookup of the threads tracking one PR. A thread opened on a fork's PR is recorded on its local `pr/N` branch, which git status never links to the PR. Cascades with the thread and is cleared from a holder. |
| `pr_list_projects` | The Pull requests page's last read of each forge repository, keyed by `git.RepoReference.Key`: `project_json`, the `ProjectPRList` the pump published (rows with their attention state and reason), and `read_at` in Unix milliseconds. Written after each repository's read by the one writer that owns the copy (the latest started of the boot prefetch and the list pumps, a pump only while it runs); deleted when no project names the repository. Cache content: a lost row costs one forge read. Not tied to a project row. |
| `thread_drafts`, `thread_tracked_files`, `new_thread_mcp_defaults` | Composer drafts, per-thread tracked-file state, and defaults applied to newly materialized threads. Each uses narrow accessors rather than the broad thread projection. |
| `attachments`, `attachment_owners` | Attachment metadata and thread ownership edges; bytes live under `internal/attachment`. The original `attachments.thread_id` names storage provenance and survives deletion of that thread while other owners remain. A pointer fork reads an ancestor's attachment while it shows a row referencing it and owns the ones on rows it copied. `kind` is the closed `image` or `file` vocabulary enforced by `InsertAttachment`. `shell` is JSON on a `file` that is the output of a composer shell command (`store.AttachmentShell`), null otherwise. |
| `proposed_plans`, `proposed_plan_comments` | Plan version and inline-review state projected into timeline item metadata. Their mutators bump the owning thread's history revision. |
| `diff_review_comments` | Review comments keyed to diff scope and location. A row belongs to a thread (`thread_id`) or, for a PR the Pull requests page reviews with no thread, to that PR (`pr_key`, PR scope only); a CHECK keeps exactly one. Accessors take a `DiffReviewOwner` and see only that owner's rows, so the thread cascade, a holder retire and a transfer export, which all key on `thread_id`, never touch a PR's. A message to a thread claims the drafts it carries before delivery (`ClaimDiffReviewCommentsSent`), matching each body it read, so an edit saved meanwhile stays a draft and a draft another message took fails the send. The claim names the message's user row (`claim_thread_id`, `claim_item_id`) and what still has to deliver it (`claim_settles`): a direct send's or steer's row insert settles it in its transaction (trigger `items_settle_diff_review_claims`, `row`); a queued message's row can land before the provider has it, so its claim settles in the transaction that writes the provider's confirmation (`confirm`, `settleDiffReviewClaimsTx`, also the Claude merge fold). The row link stays after settlement: a message the provider never consumed returns its drafts with its row, in one transaction (`RetireUndeliveredUserRow`), and the boot returns the drafts of a claim still unsettled (`ReleaseUnsettledDiffReviewClaims`). The retire returns each comment with its body, which is the one the message carries since an edit clears the claim; a requeue rebuilt from the row resends its rendered summary and claims those comments again. A resend that renders its comments from the drafts reads the ones its stale row still holds as drafts (`ListDraftDiffReviewCommentsByID` `heldBy`). An edit, a resolve or a publish of the comment clears its claim, and a transfer exports an unsettled claim's comment as a draft without the claim. `idx_diff_review_comments_pr` is the PR-owned counterpart of `idx_diff_review_comments_scope`. A range keeps its first line in `start_old_line`/`start_new_line` (a line side only). A held reply to a forge thread is side `reply`, PR scope, no line, with the thread in `reply_thread_id` and its first comment's database id in `reply_root_id`; The create call refuses a second draft reply to a thread for one owner, scope and source in the insert itself (`ErrDiffReviewReplyExists`), so the pane edits the one it holds; the table has no such constraint, because a recovery that returns a sent reply to draft (a retire, the boot release, a transfer) can leave two, and both are kept and listed. |
| `chat_bar_favorites`, `chat_model_profiles` | Legacy favorite seeds and last-used provider/model settings. Profile constraints remain aligned with thread runtime and reasoning settings. |
| `usage_ledger` | Append-only per-turn, per-model token and cost deltas. Deliberately denormalized without thread or project foreign keys so retained totals survive deletion. Any slice is safe to sum. Token-only rows are priced at read time from `internal/usagecost` by their UTC day. |
| `usage_pending` | Reported token snapshots awaiting final accounting, keyed by thread, provider process scope, segment and model. Survives interruption, restart and thread deletion. Final deltas consume matching pending tokens atomically and retire the settled turn's remaining rows; `usage_records` unions the rest with the settled ledger for queries. Pending rows carry no wire cost and are estimated like token-only rows. |
| `thread_tallies` | What each thread did over its life, for its spawn's Agents row (v155): `tool_calls`, each top-level `tool_call` it executed, once; `tokens`, what it spent itself (fresh input, cache writes and output, as a subagent counts them, cache reads not among them), its native agents' left to their own rows: the own figure each usage settlement carries (Claude's flat `result.usage`, not its subagent-inclusive `modelUsage`, which `usage_ledger` keeps; a Codex turn's usage), added by `AppendUsageAndReconcile` in its transaction. The v155 backfill counts a Codex ledger row, and a Claude one whose turn ran no native subagent; a Claude turn that ran one recorded no own figure and counts none; `turn_ms`, the time its completed turns ran, a turn a crash left open ending at its last recorded activity, not at the boot. A row a fork or a pointer fork's cut copies from its source, an import and a restore add nothing; a transfer's copy starts at zero, and a move installs the tallies its archive's header carries in place of the destination's (`installTransferTalliesTx`), none when the sender carried none. Tools are kept by a trigger, tokens by the usage settlement and `turn_ms` by the writers that end, reopen or amend a turn (`UpdateTurnCompleted`, `ReopenTurn`, `UpdateTurnLatePayload`, `RecoverCrashedTurns`), in the same transaction. A read (`ThreadTallies`) adds the running turn's `usage_pending` tokens and its time so far. Rows a revert or retention later removes stay counted. The row cascades with its thread. |
| `work_items`, `work_item_phases`, `work_item_units` | Durable workflow run, attempt, and fan-out records. State-machine and scheduling rules remain in `internal/workflow`; the store enforces structural relationships and atomic transitions. `source` is `manual`, `agent` or `call`. Migration v154 rebuilt the table without the removed workflow scheduler's `automation` source, writing each run it had started as a `manual` run with an empty `source_ref`. |
| `work_item_effects` | Idempotency ledger for first-party workflow side effects, unique by run, phase, tool, and payload hash. |
| `workflow_provider_usage_scopes`, `workflow_provider_usage_attention` | Durable attribution and notification ownership for provider-usage parks. They do not decide provider admission. |
| `scratch_threads` | Where an ephemeral `scratch` fork came from: source thread, the mode a Keep promotion returns it to, and the request it answers. The thread itself carries only mode `scratch`, which is hidden and refused by `threadmode.ValidateSet` in both directions; `PromoteScratchThread` is the only exit. Deleting the thread cascades the row. |
| `ui_state` | Opaque user/device settings plus legacy frontend-state migration buckets. `internal/settings` owns key meaning and scope derivation. |
| `push_tokens`, `push_sender` | Push destinations and sender credentials used by remote notification delivery. |
| `store_meta` | One row containing stable `backend_id` and history-lineage `replica_generation`. Restore preserves the former and remints the latter. |
| `deferred_migration_failures` | One row per migration whose deferred phase last ran with failed items: count, first error and time. Read only above the `PRAGMA user_version` watermark; a clean run clears it. Restore takes the snapshot's rows with the snapshot's watermark ([sqlite-store.md](sqlite-store.md#deferred-phases)). |

`thread_draft_recoveries` holds one staged replacement per thread until a user row
owns its SendID or recovery merges it into the composer. It is durable application
data, independent of history retention and editable drafts. Boot restores unsent
content without dispatching it. Thread deletion cascades to the recovery row.

## Authoritative identity and access

These rows cannot be recovered from provider sessions and are excluded from
provider-history reconstruction. A whole-store snapshot includes them.

| Tables | Ownership and key constraints |
|---|---|
| `users` | Accounts. A partial unique index allows at most one owner. Disabled state is durable authority. |
| `devices` | Client instances and proof-of-possession identity. Key thumbprints, passkey credential references, and nonempty local channels are uniquely indexed. Device and session liveness are evaluated together. |
| `sessions` | Device-to-user grants with JSON scopes, binding class, revocation, and activation. Paired sessions have timed access and signed claims. Local sessions have NULL expiry and a process-bound credential; `idx_sessions_local` permits one unrevoked local session per device. |
| `signing_keys` | HMAC claim-signing secrets. Older keys remain while credentials minted under them may be valid. |
| `recovery_codes` | Hashed single-use recovery credentials. A conditional `UPDATE ... RETURNING` makes consumption atomic. |
| `auth_audit` | Bounded append-only authentication audit. Attribution deliberately has no foreign keys so it can outlive deleted credentials. An update trigger rejects mutation. |
| `pairing_links` | Hashed single-use invitations plus the exact grant, proof, purpose, membership generation, and redemption outcome. |
| `refresh_secrets` | Hashed rotating renewal chain. Spent rows remain until expiry because reuse revokes the session family. |
| `passkeys` | WebAuthn credentials owned by an account, with unique credential ID, public key, relying-party identity, counters, and authenticator flags. |
| `own_devices`, `own_device_sessions` | Personal device membership, removal tombstones, generations, and admitted-session attribution. Membership replacement and session revocation commit together. |

Identity policy, proof validation, claim signing, and scope meaning belong to
`internal/identity`. The store owns durable rows, uniqueness, consumption, and
atomic revocation.

## Authoritative queues and coordination

| Tables | Ownership and key constraints |
|---|---|
| `async_questions` | Durable question and answer state keyed by thread, prompt item, and question index. Prompt text and options survive history-cache pruning. Submission claims questions and queues their user message atomically; user-item insert/meta-update triggers mark echoed answers delivered and retire their recovery queue rows. Restoration commits the draft, question state, and queue removal atomically. `async_question_revision` raises an item's `revision` (the highest of its rows') on every change of state of any of its questions; a worker's question is put to its spawner under one revision, and the spawner's answer is claimed only while the item still has it. Pending questions have no expiry. Explicit history cuts remove prompts or reopen removed answers; forks and transfers carry their surviving state. |
| `flush_queue_items` | Messages accepted by the UI while a turn blocks dispatch. The row may be the only durable copy. Successful provider dispatch or restoration into the composer removes it. Boot restores remaining rows to drafts and does not redispatch them, except a message the app wrote for a thread rather than a person, which boot discards: a loop or watch wake is recorded on its `agent_wakes` row, a worker prompt's wake (send id `agent-ask:<token>`) is dropped because its prompt ended with the worker's session, and an `agent-overflow thread send` message (send id `agent-send:<id>`) leaves a `not delivered` row in the thread's timeline. `send_id` supports idempotency but is empty for internal injection. |
| `thread_transfers` | Move/copy journal, ownership epoch, sealed-manifest identity, retries, cancellation, and cleanup status. It intentionally has no thread foreign key so history deletion cannot erase ownership. Pending incoming rows reserve their project. |
| `thread_transfer_sessions` | Native provider-session closure reserved by a transfer. The latest non-canceled reservation fences execution and import independently of cached AO history. |
| `remote_jobs` | Destination-side command acceptance and bounded receipt, including a `warning` for background processes the command left behind. Request ID and immutable fingerprint prevent a delayed retry from executing twice. Output retention may clear old tails but keeps acceptance and provenance. Boot interrupts unfinished jobs and never replays them. |
| `thread_requests` | Source-side record of one agent thread tool call: token identity, target thread or computer, state, the whole settled answer, a late reply, monotonic revision, and how the answer reached the caller: `delivered_how` for the first answer and `late_delivered_how` for the late reply, so a late reply read inline leaves the first answer's wake row named (before v155 a late delivery overwrote `delivered_how`; v155 copied that route to `late_delivered_how` and the first answer's stays as it reads). Every state change is a conditional `UPDATE ... WHERE state = ?` that reports whether it applied; a no-op is a lost race, not an error. Partial indexes serve the remote poller, the undelivered-wake retry and the reminder clock, so their predicates appear explicitly in their queries. `polling` is the poller's gate and part of `idx_thread_requests_poll`, so a settled request with nothing left to report leaves the due set instead of costing a call every few seconds until retention; `wake_attempts`, `wake_next_check` and `wake_issue` pace and bound the retry of a wake the settlement could not hand over; `confirmed_at` and `late_confirmed_at` record the provider's echo of a queued answer and late reply (an inline delivery is confirmed by its mark), and a delivery without one is given back at boot or by the End Session or archive that ends the session holding it, while a confirmed one never is, even when its queue row outlived the echo (v155 recorded a delivery before it as confirmed only when the previous version read its message delivered: no unconfirmed row carrying it, and its queue row gone or beside a row carrying the provider's id); `wake_item_id` and `late_wake_item_id` name the caller's timeline row the echo confirmed, which a queue-boundary merge moves to its survivor and a give-back clears, so the Agents segment and the tool rows read the row that carried an answer from the request while the caller's own rows still hold it (v155 filled them for the deliveries before it from the send-id lookup); `target_thread_title` and `target_provider` carry the answering thread's name and provider when that thread is on another computer and has no row here; `delivered_with` (v149) is the token of the request whose message carried this request's answer when one wake answered several, empty when the request's own message did, with a partial index for the boot lookup from a restored message to the requests it carried; `nested_open` records whether a remote spawn's computer last listed open work under it in an `agent_rows` answer, which keeps a settled spawn in the Agents segment and on the sweep until it lists none, the sweep paging through them on `idx_thread_requests_nested_open` from the last one it asked about, and through the others at a slower pace on `idx_thread_requests_remote_rest`, to find a thread there continued after it rested, and a computer no longer paired has it cleared on every spawn to it; `answer_agent` and `answer_agent_role` are copied from the receipt with the answer, and `late_reply_agent` and `late_reply_agent_role` with a late reply, so each wake names a standing agent the same way from either computer (a flag, since an agent may have no role line); a row written before v155 reads as answered by no agent. A local spawn row is also the lineage record that names a spawned thread's owner (`idx_thread_requests_spawn_target`), so while the thread it created exists the retention sweep keeps it past the floor instead of deleting it (a local spawn is not past the floor until the app reads its thread and every thread below it at rest, by the rule in [standing-agents.md](../specs/standing-agents.md#owned-workers), and names it to the sweep's write, `DeleteThreadRequestsBefore`; a remote one while `nested_open` is set): `lineage_only` is set and the answer, late reply, answering agent, wake, `nested_open`, `target_provider` and `polling` are cleared. A remote spawn that named its thread there is kept the same way, as that thread's link here, with no thread here to check: the rest pass keeps asking about it, `nested_open` is recorded on it as on the spawn, and it is deleted when that computer refuses the thread as gone (`DeleteRemoteSpawnLineage`) or is forgotten (`ForgetRemoteSpawnsOnComputer`), or with its caller. The ledger reads (`GetThreadRequest`, `GetThreadRequests`, `ListThreadRequestsByCaller`) skip a lineage-only row, so its token is unknown to the thread tools as a deleted row's is, and the writers that could store a late reply, re-arm a wake, or give back or confirm a delivery leave it alone, as does the boot sweep of unconfirmed deliveries; the lineage reads do not filter it. A lineage-only spawn is still its thread's link into the Agents tree, so work a worker opens after the sweep nests under its owner, and Stop reaches into it. The Agents segment's read is a union of arms, each searched by caller through an index, or a range of one, that leaves the caller's settled history out: `idx_thread_requests_open_created` for open rows in tree order, `idx_thread_requests_caller_settled` for rows settled inside the window, `idx_thread_requests_open_below` for the local spawns kept for open work under them, `idx_thread_requests_nested_caller` for remote spawns with open work, and `idx_thread_requests_open_deep`, the local spawns whose marks hold work three spawns below their target, from which the reads climb to the spawns above that no mark reaches. `idx_thread_requests_caller_settled` holds every row, lineage rows included, keyed `(caller_thread_id, settled_at, token)`, so the segment's Past list pages a caller's settled rows newest first from a cursor in index order. A thread is reached by at most one local spawn, its link (`idx_thread_requests_spawn_link`, unique over the spawns not `superseded`; v155 kept the newest of any two, by creation time then token, as the link and marked the older `superseded` and lineage-only). The link is the one ownership relation: the spawner `threadColumns`, `SpawnOwnerOf`, the search's spawned-by filter and an answer's read mark name, the owner an archive and a delete cascade by (`ListOwnedWorkersToArchive`, `ListDeleteFamily`, `ClaimDeleteFamily`), and what owned placement needs (`spawnerOfSQL`); a `superseded` row names no owner, and `open_below_0` to `open_below_3` count, on each such spawn, the open work the threads 0 to 3 spawns below its target made, kept by triggers (v155). The retention sweep reads the oldest age past which it could act through `idx_thread_requests_age` and `idx_thread_request_receipts_age`, and the local lineage rows whose thread is gone through `idx_thread_requests_lineage`, and takes no write transaction when nothing is due. `made_in_thread_id` is the past thread that made a request a handoff moved to its assistant's current thread (`caller_thread_id`), empty when the caller made it; a destination's receipts name it as the source. `spawn_instructions` (v155) is what a spawn's thread was made with: a local spawn's is written in the transaction that names its thread, a remote one's from the destination's answer when the poll or reply first collects it, and a spawn's reply reads it. `idx_thread_requests_answer_due` (v155) holds, by caller, the settled rows whose answer is on its way to the caller: owed as a message and not delivered, or delivered and not yet confirmed, first answer or late reply; the caller is not at rest while one is (`ThreadAnswerDue`), and the Agents tree's held work seeds from it. `rest_unreported` (v155) marks a `finished` answer a paired computer gave for a spawn, or a send to a thread the caller spawned there, from a version that settles it when its turn ends and cannot report whether the thread came to rest. `owner_op_seq` (v158) numbers the owner operations owed for a remote spawn (`thread_owner_ops`), and `idx_thread_requests_remote_spawn_target` finds the remote spawn that named a thread on a computer (`RemoteSpawnLinkTo`). `idx_thread_requests_spawn_caller` (v159) holds the local spawns that link a thread (not `superseded`, target named) by caller, so a walk from a thread down its spawn links reads only the links, whatever the caller's send and ask history: the subtree read behind a decision on rest (`ReadSubtreeRest`) and the owned walks. |
| `thread_request_receipts` | Destination-side record for the same token, keyed by it so a retried delivery finds the acceptance it already made and spawns nothing. `target_thread_id` is NULL for a spawn or ask until the thread or scratch fork exists, and is named once afterwards; the boot sweep settles an untargeted acceptance like any other open receipt. It binds settlement to the turn the request's message was delivered into (`turn_id`, empty while a message handed to the provider waits for its delivery; `own_turn` when that turn opened for the message, the only turn a cancel interrupts), and holds the answer of record until the source acknowledges the revision; `answer_agent` and `answer_agent_role` record whether the target was a standing agent, and its role line, when the answer was written, and `late_reply_agent` and `late_reply_agent_role` the same for the late reply. An uncollected answer expires after a day; the row stays until the retention floor so the token keeps answering. A spawn's receipt is also what authorizes the source's forwarded `agent_rows` and `agent_stop` for its thread (`ThreadSpawnedForSource`), so it is not past the floor until the app reads that thread and every thread below it at rest, by the rule in [standing-agents.md](../specs/standing-agents.md#owned-workers), and names it to the sweep's write, and past the floor, while that thread exists, the sweep keeps it as `lineage_only` (v155) with its answer, late reply and answering agent cleared; the ack, the get and the per-thread list skip a lineage-only receipt, so its token is unknown to the ledger as a deleted one's is, and the sweep deletes one whose thread is gone through `idx_thread_request_receipts_lineage`. A request between two threads of this computer writes its source row and receipt in one transaction (`AcceptLocalThreadRequest`): a send `accepted` and naming its thread, a spawn or ask `unconfirmed` until the thread it creates is named on both rows and the source row accepted in one more (`NameLocalThreadRequestTarget`); the dispatch mark and the turn binding move the source row to `running` in their own; a settlement writes the receipt, a source row on this computer and the acknowledgement in one (`SettleLocalThreadRequest`). `spawn_instructions` (v155) is the spawn's thread's `spawn_instructions`, recorded in the transaction that names it (`NameLocalThreadRequestTarget`, `SetThreadReceiptTarget`), so a retry and a recovered status state them after the thread is gone. `spawn_link` (v158) marks a paired computer's owned spawn: while it is set and its thread is owned, the thread belongs to the receipt's source thread there (`SpawnOwnerOf`, `Thread.SpawnedByComputerID`), at most one link per thread (`idx_thread_request_receipts_spawn_link`), and the naming write owns the thread (`SetThreadReceiptTarget` with own). The receipt insert sets it only while its device holds an unrevoked session here, so a spawn from a device without one is a plain receipt and its thread standalone. A link ends when its device holds no unrevoked session here, in the transaction of the write that revoked or deleted the last one: every store write that ends sessions (a session or device revocation, a personal-group merge, a retired introduction or pending pairing, the credential prune of sessions past their refresh window, a device deletion) goes through `endSessionsTx`, which releases those devices' links and returns their threads, and a revoked device's own links go with it even when no session moved. Expiry alone ends no link, since an expired session renews through its refresh secret. A link also ends when `owner_seen_at`, written at acceptance and moved at most hourly by the owner's calls whatever its thread's placement (`ReachSpawnLink`), and the receipt's creation are both past the retention floor (`idx_thread_request_receipts_owner_seen`, one link at a time whatever its device), or when its owner releases it (`ReleaseSpawnLink`). `owner_op_seq` is the newest owner operation the link admitted (`SupersedeLink`). A settled receipt names no thread it had not named before it settled (`SetThreadReceiptTarget`), and one it named stays for lineage. The lineage clearing keeps all three. |
| `thread_owner_ops` | Source-side operations owed to a paired computer for one remote spawn (v158), keyed by the spawn's token: `archive`, `delete`, `release` (the owner was given to another computer, whose cleanup deletes none of the workers it left) or `supersede`, with the sequence it took from the spawn row's `owner_op_seq`, whether it was attempted at that sequence (`sent`), when it was owed and when it is next due (`idx_thread_owner_ops_due`, `ThreadRequestSchedule.OwnerOp`), and its attempts, which pace the retry. It has no foreign key: a delete's rows, owed in `CommitDeleteClaim`'s transaction for every remote spawn of the threads it committed, outlive the spawn rows that cascade with their caller. A delete replaces any owed operation and nothing replaces a delete. Unarchiving a thread withdraws the archives owed for the spawns it made, in the unarchive's transaction: an unsent one is dropped and a sent one becomes a `supersede` at the spawn's next sequence. The delivery writes (`MarkOwnerOpSent`, `RescheduleOwnerOp`, `SettleOwnerOp`) name the sequence they act on, so an answer to a replaced operation changes nothing. Forgetting the computer drops its rows (`idx_thread_owner_ops_computer`); a snapshot restore keeps them. |
| `agents` | An assistant (a standing agent): its own id, its current thread (`thread_id`, unique), its home directory `<config>/agents/<id>`, the assistant that created it (`creator_agent_id`, empty when the user did) and whether it serves every project on the computer (`all_projects`). Cascades from the current thread, so deleting that thread deletes the assistant. The current thread does not move to another computer: `CreateThreadTransfer` refuses its outgoing move and `AdvanceThreadTransfer` its commit (`ErrAssistantThreadStays`). The record's delete refuses while a past thread or helper is under it (`AssistantDependentsError`); a delete's claim of the current thread refuses a handoff, its commit refuses a new helper, and the row drops last. A handoff points `thread_id` at the successor ([standing-agents.md](../specs/standing-agents.md#standing-agent)). |
| `agent_projects` | The projects an assistant serves when `all_projects` is not set (`WITHOUT ROWID`). Cascades from the assistant and from the project ([standing-agents.md](../specs/standing-agents.md#standing-agent)). |
| `agent_helpers` | The threads an assistant made for its own work outside every project: a spawn without a project and a fork of a thread under it. Cascades from the thread and from the assistant; the assistant's delete deletes its helpers' threads first. A helper's thread has no project (`ErrHelperInProject`). |
| `agent_past_threads` | The threads an assistant had before its current one, with when each was superseded, paged newest first by `idx_agent_past_threads_agent` (`ListAssistantPastThreads`). Cascades from the thread and from the assistant: deleting a past thread leaves the assistant, and the assistant's delete deletes its past threads first. The retention sweep skips current and past threads alike. `moved_draft` and `moved_draft_attachments` are the text and attachment ids of the composer draft the handoff moved to the next thread, written in the transaction that moves it (`HandOffThreadDraft`); a send of that text from the past thread is refused as moved. |
| `agent_wakes` | A thread's loops and watches, the wake supervisor's whole schedule: no provider history rebuilds it, and boot reloads every `armed` or `running` row. `state` is the supervisor's execution, not the agent's turn: `running` is a script in flight, a long-running process alive, or a fire between its claim and its queueing, which is what tells boot a quit cut the run. A label is unique among a thread's live rows, and a thread keeps at most 64 live rows. A cancelled row is kept only so its label revives with its id: a cancel clears its `last_output` and `last_stderr` and leaves the thread its 16 newest cancelled rows. `idx_agent_wakes_thread` serves every per-thread read and write. `timeout_seconds` bounds one run of an interval watch. `last_output` keeps, capped at 64 KiB, the data of the watch's latest wake that never reached the thread, until a later undelivered wake replaces it or the label is registered again. `undelivered` is that wake's outcome, kept apart from `last_outcome` so a run that wakes nothing cannot erase it, and cleared when a later wake of the row reaches the queue; while it holds a skip, `missed` carries into the next wake's count. `last_stderr` keeps, capped at 8 KiB, the tail of a watch's last run's stderr (a long-running watch's latest non-empty batch) for the background tray, and is cleared when the label is registered again. `failure_noticed_at` is when the notification that the watch keeps failing (`watch:<id>`) was raised, written before it is raised and cleared after its withdrawal is queued; boot reads the live rows that hold it so the run that ends the failure after a restart withdraws it. A wake's queue row carries the send id `agent-wake:<id>:<fire>`, and `QueueAgentWake` refuses a second while one is queued. |
| `session_start_failures` | A thread whose session, started for a message the app queued, failed to start and raised the start-failure notification (`session-start:<thread>`). Written before the notification is raised and deleted by the first successful start after the withdrawal is queued; boot loads the rows so a start after a restart withdraws a notification raised before it. Cascades from the thread. |
| `remote_watches` | Source-side monitoring and notification ownership, with the job's `label` and its `command` display text. Registration precedes the network call. Terminal observations are monotonic. Queueing a completion and inserting its `flush_queue_items` row is one transaction. `confirmed_at` records the provider's echo of the queued completion, and a completion without one is given back at boot or by the End Session or archive that ends the session holding it, while a confirmed one never is (v154 recorded a completion queued before it as confirmed by the rule v155 applies to answers); `wake_attempts` paces the redelivery of one a session end gave back, and `wake_issue` says why delivery was given up. `cancel_owed_at` is when a cancel the destination did not take was first owed (0 when none is) and `cancel_next_at` when the watcher sends it again, through `idx_remote_watches_cancel_owed`, and `stopped_at` when a rest or an archive dismissed the completion, a dismissal nothing brings back, where the dismissal of a refused start gives way to proof the destination accepted it (since v156); a watch whose cancel is owed is neither polled nor delivered. `thread_id` is the thread that receives the completion; `launched_in_thread_id` is the thread that launched the job and that the destination's receipt names as its source, which an assistant handoff leaves in place when it moves `thread_id`. A watch cascades from `thread_id` (since v154), so a deleted thread's watch leaves the watcher's due list with it. The retention sweep deletes a watch with nothing left to deliver (dismissed, or queued and confirmed) at the request ledger's 30-day floor from its creation, through `idx_remote_watches_done`. |

`RestoreFrom` refuses replacement while active commands or transfer phases make
it unsafe. It preserves the live transfer journal, reserved transfer sessions,
remote command receipts, remote watches, and thread requests and receipts
instead of replacing them from the snapshot. It also rejects snapshots that predate current incoming transfer
ownership.

## Important indexes

Most indexes follow directly from an accessor's filter and ordering. The
following families carry additional correctness or performance meaning:

| Index family | Contract |
|---|---|
| Timeline ordering and import indexes | `idx_items_thread_turn_item_unique` enforces one mutable row per timeline coordinate. Import indexes and triggers keep chunk order and identities unambiguous. `idx_thread_import_chunks_turns` and `idx_thread_import_chunks_newest` range a thread's references by turn, oldest and newest first. A limited imported arm that walks the references walks the one in its read's order (`chunkRefsIndex`), so once its sorter holds the limit it reads each other chunk only up to its first selected row. |
| Key-first imported lookup indexes | `idx_import_history_items_id`, `idx_import_history_payloads_id` and the imported parent, completion, task, send-id and transcript-root lookup indexes lead with the key and end with `chunk_id`. A lookup reads the matching rows and checks each chunk's membership in the thread, whatever number of chunks the thread references. The ID indexes also serve the chunk-admission collision probes, including chunks sharing a turn. |
| Attachment ownership index | `idx_attachment_owners_attachment` supports last-owner collection and retained-file lookup. |
| Pointer-fork indexes | `idx_thread_fork_lineage_ancestor` finds the forks that read a written row by its position, so a source write past every cut probes no fork, and gives a delete the latest cut of the forks that read the thread. `idx_items_unsettled` gives fork creation the source's running and streaming rows. `idx_items_attachment_refs` and `idx_import_history_items_attachment_refs` hold only rows whose meta lists attachments, so a fork's ownership check reads those rows, not every inherited row; their `instr` predicate must appear in the query. |
| Sparse send identity indexes | Local items, imported items, and queued messages index nonempty `sendId` values so retry checks do not scan or hydrate history. |
| Scoped timeline indexes | Parent indexes include timeline coordinates for ordered child pages. `idx_import_history_items_parent_lookup` starts recursive imported-child lookups by parent identity before checking chunk membership. `idx_items_scope_lifecycle` and its imported counterpart select the latest resume carrier without scanning a transcript. |
| Turn-error indexes | `idx_items_thread_error` and `idx_import_history_items_error` hold only `error` rows, so the turn-error triggers recompute a thread's pair with one probe per arm and per attached chunk. |
| Subagent aggregate indexes | `idx_items_subagent_resume_prompt` finds the resume prompts under an anchor: the rounds a card or a recompute reads, and the prompt a carrier stored after it names (`subagentPromptNamesSQL`). `idx_subagent_aggregates_dirty` finds a thread's dirty anchors by key for `RecomputeSubagentAggregates`. `idx_items_running_nested_fg_tool_calls` holds the nested foreground calls in flight, which `ListLiveBackgroundTasks` walks up to their background launch instead of walking every launch's subtree down. |
| Agent stop indexes | `idx_items_completion_of` orders a launch's completion siblings by `created_at, turn_index, item_index`, so a launch's newest stop is one index step however many runs it had (`newestStopIDSQL`: the tray's run state and `CurrentParkedStop`). `idx_items_subagent_wake` holds the wake rows under each transcript root by `created_at`; its predicate is `wakeFlagSQL`'s, which the wake probe must state. |
| Top-level timeline indexes | `idx_items_top_level` and `idx_import_history_items_top_level` hold the visible rows with no parent (not `plan_update` notifications), in timeline order, with the visibility filter's columns and the id. A main-timeline arm (`mainTimelineFilterFor`), a fork's lineage arms included, walks them instead of the ordering index, so a page, run expansion or held-window check reads no subagent child row. An arm uses them only when it states both terms and projects no column they lack: `topLevelItemsFilterFor` alone, or a projected `rev`, walks the ordering index (`windowDigestRowsTx` reads `rev` by rowid after the walk). `TestMainTimelineArmsWalkTopLevelIndexes` pins the plans of the statements those reads run. |
| Provider item index | `idx_items_provider_item` holds the rows whose meta carries a `provider_item_id`, keyed by thread, that id and turn. A settled assistant block that never streamed, which is every text and thinking block of a background agent, finds its row through it (`FindStreamItemByProviderItemID`) instead of reading the turn. |
| Summary-only diff index | `idx_payloads_summary_only_diff` holds the `tool_result` payloads whose inline diff is `summary_only`. A Codex turn diff, which arrives after every file change, finds the live turn's upgradable rows among the thread's summary-only payloads through it (`ListTurnSummaryOnlyDiffItems`, predicate `summaryOnlyDiffPayloadSQL`) instead of reading the turn. |
| Thread find indexes | `idx_items_thread_rev` serves a find refresh's read of the rows whose `rev` passed its last answer; its `rev IS NOT NULL` predicate keeps every read that does not compare `rev` off it. `idx_items_find_text_pending` and `idx_import_history_items_find_text_pending` hold the rows migration v150's deferred backfill, which v157's phase runs again and which recreates them first, has not filled, and are dropped when it finishes. |
| Item relationship partial indexes | Parent, completion, live-background, running-foreground, and reader-authored-message indexes require their qualifying predicate to appear explicitly in query SQL. |
| Workflow relationship indexes | Agent source references are unique; parent-run, phase-thread, unit-thread, state, and usage indexes bound recovery and budget queries. Partial predicates such as `parent_item_id <> ''` and `source_ref <> ''` remain explicit. |
| Credential lookup indexes | Owner uniqueness, credential hashes, live sessions, passkey IDs, device proofs, channels, and refresh families make authorization and single-use consumption indexed atomic operations. |
| Coordination indexes | Transfer ownership/retry, active and settled remote jobs, pending watches, and thread watch discovery bound recovery work independently of conversation size. |

When index selection is part of behavior, tests assert both result parity and
`EXPLAIN QUERY PLAN`. See [sqlite-store.md](sqlite-store.md#query-plans).

## Triggers

| Family | Purpose |
|---|---|
| History revision | Three `items` triggers maintain `threads.history_rev`, `threads.history_epoch`, and the per-row `items.rev` stamp on every row whose read result the write changed: the row, its completion sibling, and the anchors decorated from its parent chain and their completion siblings, never a parked sibling, which records one run and borrows no card (`stampedRowIDsSQL`: a recursive CTE walks the chain by primary key; the carrier leg probes the partial expression index `idx_items_transcript_root` by root id). They do no subagent card work: the store keeps the cards in Go (`subagent_card.go`). Only the row stamp writes `rev`. The update trigger fires on every column but `rev`, so a stamp does not re-bump the thread. |
| Subagent stamp | Two `subagent_aggregates` triggers stamp the anchor a row write changed, and its completion siblings but a parked one, which borrow its card, with the thread's `history_rev`. `RestoreFrom` drops them for the row copy and reinstalls them. |
| Turn error | Triggers on `items`, `turns`, `thread_import_chunks` and `thread_import_item_overrides` keep `threads.newest_turn_error_at` and `newest_turn_error_turn`: the newest `created_at` and `turn_index` of the visible `error` rows at or after the newest turn (`thread_turn_error_aggregate.go`). `hasFailedTurn` and `MarkThreadReadNow` read the pair, so a thread-row read does no timeline probe. The chunk-detach trigger runs before the delete, while the chunk's rows exist. |
| Find text | `findTextTriggersSQL` keeps `find_text` current: on an item insert or a change to its text, meta, kind, tool or payload; on a payload's insert or a change to its data or meta, for the reasoning and tool rows that show it; and on an append chunk, which appends its loose form to the reasoning rows that show the payload. A row streaming reasoning keeps its text until it settles. Writers that supply `find_text` inline skip the second write. `RestoreFrom` drops them for the copy and reinstalls them. |
| Payload collection | Item deletion removes payloads no longer referenced by either payload field in the same thread. Cascades collect payload chunks and edit snapshots. |
| Imported-history integrity | Triggers reject implicit shadowing, coordinate overlap, chunk gaps, and ambiguous payload identity; the final thread reference collects immutable storage. |
| Pointer forks | `forkTriggersSQL`: refuse a write that changes a row, payload, append chunk or turn row a fork shows, hide rows an ancestor inserts or moves below a fork's cut, keep a fork's own rows at or after its cut, refuse to delete a thread forks read, and mark a holder no fork reads for deletion ([sqlite-store.md](sqlite-store.md#triggers-and-stamps)). The payload guards and the item update guard pass a migration's data fix while `shown_history_fix` holds its row. |
| Attachment ownership | Initial insertion creates the origin owner. Removing the final owner collects metadata; the attachment package releases file bytes. |
| Background settlement | Three triggers set `meta.live_background_active` false as launches and ending completion siblings arrive or change; a `parked` sibling settles nothing, and a settled launch stays settled ([sqlite-store.md](sqlite-store.md#schema-owned-invariants)). |
| Authentication audit | A before-update trigger makes `auth_audit` append-only. |
| Agent tree marks | Three `thread_requests` triggers keep each local spawn's `open_below_*` counts in the transaction of every write that adds, removes, settles, re-arms, moves or retargets a request, a thread delete's cascade included, climbing at most four spawns through the one that reaches each thread; two refuse a local spawn that reaches its caller or a thread within four spawns above it, a cycle whose paths the counts would repeat (migration v155). |
| Thread tallies | `trg_items_tally_tool_calls` counts each top-level `tool_call` insert into `thread_tallies` outside a bulk history load (a fork's copy, an import, a transfer's import) (migration v155). Restore suspends it for its copy, so the snapshot's tallies land as they are. |

Do not reproduce these invariants in Go write paths. Restore temporarily removes
the item-derived trigger sets for its bulk copy and recreates them from the
shared latest-schema constants.

## Migration policy

Migrations are numbered, forward-only, and append-only. Never edit a migration
that may have shipped. Add a new migration, preserve all current columns,
indexes, triggers, and child relationships in rebuilds, and add a test that
proves the resulting constraint behavior. Detailed rules live in
[sqlite-store.md](sqlite-store.md#migration-model).
